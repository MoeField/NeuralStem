### ★ 已修复：Demucs 完整歌 Java 堆 OOM（BF00A + Gen3 均复现）

- **根因（Gen3 native crash dump 实证）**：`DemucsSeparator.acc = Array(4){Array(2){FloatArray(total)}}`
  （5:14 = **443MB** 常驻 Java 堆）+ 每块 `float[][]` 44MB → 撞 Java 堆 512MB 上限（与设备 RAM 无关）。
- ✅ **已修（`fc463cf`）**：acc 改**滑动窗口** O(WAVE)≈7MB（块处理完 [sB,sB+step) 即归一化+落盘+丢弃）。
- **验证**（BF00A 完整歌 5:14）：修复前 ~8s OOM 崩；修复后 `demucs done: in=out=13849391
  blocks=54, infer=516803ms realtime=0.61x, peakPss=4933.9MB`（native ORT arena），4 轨等长 ✅。
- 遗留（非阻塞）：native PSS **~4.9GB**（ORT 固有，M4 已知）。

### ★ 待观察（不占精力；若再遇到再查）：2-stem “回声/疑似偏移”

- **现象**：用户某首歌 2-stem 听到“回声感”（关掉一轨消失）→ 疑两轨错开。
- **用户复现**：**其他几首歌复现失败**（非系统性问题）。
- **量化（互相关）**：该曲 voc/acc **整体 lag = 0**（长度也相等）；局部 lag≠0 的窗口
  **ncc 均 ≤0.22（低相干）** → 属坑 38/39 的“低相关窗伪影”，非真偏移。⇒ 更可能是
  **Spleeter 渗漏**（同一人声成分出现在两轨 → 叠加有梳状/回声感），属音质范畴。
- **决策**：**先不管**（复现失败 + 无稳定病征 + 指向音质非 bug），记录待观察。

### ★ 待办 B1：切换模式时的 prepare 空白（架构级，暂不做）

**现象**：关多轨回原曲时，新 MediaItem 需 `prepare()` → 约 2 秒无声
（进度条跳 0 的**可见部分**已于 2026-10-19 用“seek 锁定 + duration 沿用”掩盖）。

**已排除的方案**：
- ❌ **弹窗“加载中”**：只是掩盖，体验倒退。
- ❌ **全轨常驻 + 静音切换**：**无法消除空白** —— 空白来自“换 MediaItem 必须 prepare”，
  不是“轨不够”。而且 `MediaSession` 只能认 1 个 player（坑 45）。

**唯一可行方案（B1）：让 `singlePlayer` 永远播【原曲 mp3】**

```
现在：singlePlayer = 当前出声者（单轨播 mp3 / 多轨播 vocals stem）
B1  ：singlePlayer = 永远播 mp3（session 认它）
      跟随轨 = vocals / accompaniment（进多轨时创建）
      切模式 = 改各轨音量（原曲 1↔0，stem 0↔1），**不换 MediaItem**
```

**收益**：关多轨**永不 prepare**（原曲从未停过）→ 无空白、无位置跳变。

**改动估算（~135 行）**：`PlaybackService.handleLoadMultiTrack/handleExit`、
`MultiTrackController`（主轨语义从“其中一条”改为“静音伴跑”）、
`PlayerViewModel.toggleSeparation`（删掉 doLoad 重载）、EQ 多挂一份。

**风险**：
1. ⚠️ **推翻 M3 v2 架构**（“session 认 singlePlayer，多轨时它是主轨”）：
   通知标题、EQ 挂载、`MultiTrackSession` 协议都要跟改。
2. ⚠️ 单轨时 stem player 若常驻会占解码器（Android 解码器有限，通常 8–16 个）。
3. ⚠️ 音量 1→0 硬切可能爆音，需 ~50ms 渐变。
4. ⚠️ 主轨与跟随轨长时间自由播放的**漂移**未测（V1/S1 只验了 seek 后对齐）。

**决策**：**先不做**。待功能稳定后作为独立阶段评估（距交付 ~6 周）。
