## 1. 跨设备：三引擎全对比（核心表）

> 音频：120s（Demucs 为 7.8s 窗，探针口径）

| 引擎 | BF00A | Gen3 | Gen3 加速 | 内存（PSS） |
|---|---|---|---|---|
| **Spleeter 2-stem**（默认） | 7.9× | **15.0×** | 1.9× | ~740 MB |
| **Spleeter 4-stem** | 2.22× | **3.67×** | 1.65× | 1122 / 1182 MB |
| **Demucs (htdemucs)** | 0.82× | **1.83×** | 2.24× | ~5.0 GB（ORT arena） |

### 结论

1. **Demucs 在 Gen3 上首次突破 1× 实时**（0.82× → 1.83×，**2.24×**）。
   4 分钟歌估算：BF00A ~4.6 min → **Gen3 ~1.9 min**。
2. **Gen3 对 Demucs 的加速（2.24×）> 对 Spleeter（1.65–1.9×）**
   —— Demucs 计算密度更高，更能吃旗舰 CPU 吞吐。
3. **产品策略（按设备档位暴露引擎）**：

   | 档位 | 默认 | 可选 |
   |---|---|---|
   | 中端（RTF ~8） | Spleeter 2-stem | 4-stem（2.2×，可接受） |
   | **旗舰（RTF ~15）** | Spleeter 2-stem | **4-stem + Demucs 音质档** |

   ⇒ 印证 M2「按 RTF 分档暴露引擎」的设计。

## 4. 正确性判据（各引擎不同，**不能混用**）

| 引擎 | 判据 | 实测值 | 说明 |
|---|---|---|---|
| Spleeter 2-stem | 能量守恒残差 | 1.4%–13.3%（因曲而异） | 软掩码模型正常范围 |
| **Spleeter 4-stem** | `sum(4 stems) − mix` | 桌面 **−163.5 dB** / 真机 **−71.0 dB** | 真机低是 PCM16 量化所致 |
| **Demucs** | **NCC vs 参考实现**（**不能用能量守恒！**） | 单窗 NCC **0.9996–1.0000** | 见下注 |

> [!WARNING]
> **Demucs 不含「mask 和为 1」约束**（独立预测各源），`sum(4) − mix = **−31 dB**` 是其**正常水平**，
> 不能用 Spleeter 的 −153 dB 判据。正确做法是 **NCC / 与参考实现逐窗对比**。
> 另：多块拼接产物**必须逐窗对比**，整段逐样本比会因块相位不同而对不齐。

## 6. 性能优化（Gen3，40s / 120s）

### 6.1 Demucs 阶段耗时分解（40s / 7 块，threads=4）

| 阶段 | 耗时 | 占比 |
|---|---|---|
| read | 90 ms | 0.2% |
| STFT | 1377 ms | 3.7% |
| **model（ORT）** | **26701 ms** | **70.7%** |
| **iSTFT** | **8233 ms** | **21.8%** |
| accum | 311 ms | 0.8% |

### 6.2 线程数扫描（针对 70% 的 model）

| threads | inferMs（40s） | 备注 |
|---|---|---|
| 4 | 38.5 s | |
| **6** | **32.3–35.5 s** | ✅ **最快（默认）** |
| 8 | 46.7–51.2 s | ❌ 超订（大小核 + 系统争抢） |

### 6.3 优化累计

| 版本 | model | iSTFT | total（40s） | 实时 |
|---|---|---|---|---|
| 原始（threads=4） | 26.7 s | 8.4 s | ~38.5 s | 1.04× |
| + 线程 6 | — | — | 32.2 s | 1.24× |
| **+ iSTFT 并行** | 25.3 s | 2.1 s | **29.6 s** | **1.35×** |

**iSTFT 并行效果**：`~8200ms → 2085ms`（快 ~4×，近理想加速）。
正确性：逐样本 NCC（旧串行 vs 新并行）= **1.000000**（4 轨全部）。

### 6.4 Spleeter 4-stem 同手法（收益更大）

| | 优化前 | 优化后 |
|---|---|---|
| 120s 总推理 | 32724 ms | **17320 ms** |
| 实时 | 3.67× | **6.93×** |

⇒ 快 ~1.9×。正确性：`sum(4)−mix = −69.9 dB` ✅。

### 6.5 优化手段汇总

| 手段 | 收益 |
|---|---|
| 线程 4 → **6** | ~15%（8 线程反而超订变慢） |
| **FFT twiddle 预计算** | iSTFT ~10–15% |
| **iSTFT 按 stem 并行**（4 线程池） | iSTFT ~4×，总计 ~23%（Demucs）/ 1.9×（4-stem） |

## 7. GPU / NPU 上限实测（决定性表格）

> 方法：独立 `:bench` 模块（不引 sherpa），`onnxruntime-android-qnn:1.29.0`，
> Java API 加载同一个 `htdemucs_embedded.onnx`，逐 EP 跑同一 7.8s 窗（预热后 3 次取中位）。

| EP | 中位 | 实时 | vs CPU |
|---|---|---|---|
| **CPU**（ORT 1.29.0） | 4237 ms | 1.84× | 基线 |
| **QNN（骁龙 NPU）** | **3290 ms** | **2.37×** | **1.29×** |
| NNAPI | ❌ 未编入 | — | `"not compiled with NNAPI support"` |
| XNNPACK | ❌ 未编入 | — | `"not supported in this build"` |

### 结论（报告可直接引用）

1. **骁龙 NPU（QNN）实测只有 ~1.3×** —— 远低于乐观预期（3–8×）。
   原因：htdemucs 含大量**非标准算子回退 CPU**，QNN 只吃 conv/gemm；加上 CPU↔NPU 数据搬运。
2. NNAPI 另一条路：sherpa ORT 虽导出该 EP，但 htdemucs 图被切成 **131 个分区** →
   同 40s 音频 **130s+ 未跑完**（CPU 仅 33s）⇒ **不可用**。
3. ⇒ **实测坐实「不值得为 GPU/NPU 重构」**：上限仅 ~1.3×，且换 EP 还要解开坑 49 的符号死结。

## 8. 内存

| 场景 | 数值 | 性质 |
|---|---|---|
| Demucs 空载 PSS | 137 MB | — |
| **Demucs 运行峰值** | **5045 MB（+4.9 GB）** | ⚠️ ORT CPU arena 固有 |
| Spleeter 4-stem 峰值 | 1122 MB（中端）/ 1182 MB（Gen3） | 4 会话常驻 |

**Demucs 内存诊断（排除我方代码）**：

| 实验 | 结果 |
|---|---|
| 8s（2 块） vs 40s（7 块） | PSS **5019 vs 5045 MB** ⇒ **与块数无关**（非累积泄漏） |
| 去掉每源 `copyOfRange` | 无变化 |
| `session.use_env_allocators=0` | 无变化 |
| `arena_extend_strategy=kSameAsRequested` | 无变化 |

⇒ **~4.9 GB 是 ORT 跑 htdemucs 大激活张量的固有开销**，无会话级旋钮可调。
Gen3 16 GB 上可接受，中端 12 GB 上偏紧。**接受现状，不硬攻。**

> [!NOTE]
> 与 Java 堆 OOM 是两回事。Java 堆 OOM（`DemucsSeparator.acc` 443 MB 常驻）已由
> `fc463cf` 改为滑动窗口 O(WAVE)≈7 MB 修复。**native PSS ≠ Java 堆。**

## 9. 多轨对齐（S1，与 M4 一并验证）

| 判据 | 结果 |
|---|---|
| 文件级对齐（离线互相关，57 窗） | **lag = 0 采样点** ✅ |
| seek 后立即暂停读 `currentPosition` | **0 ms 差**（2/2 次） |
| 播放中观测的 ~200 ms 差 | **估计伪影**，非真实错位 |
| 输出线程 | 两轨在**同一 MixerThread**（`AudioOut_15`） |

> 若真有 200 ms 内容偏移，播放 1 s 就产生 12.6% 速率差 → 会明显变调，**物理上不可能**。
