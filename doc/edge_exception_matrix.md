## 已修的 bug（验证过程中发现）

### Bug A：两阶段之间留 900 帧空洞
- **现象**：`ranges=[[0,4129770],[4130670,6639182]]`
- **根因**：块拼接 0.5s 交叉淡化，最后一块的尾部 overlap 区不写进 `onWrite`
- **修法**：阶段 2 的 `endFrame` 加 `DEFAULT_OVERLAP_FRAMES` 余量

### Bug B：续算时产生新的空洞
- **现象**：`ranges=[[0,22050],[112014,6639704]]`（差 2 秒）
- **根因**：阶段 2 硬编码补 `[0, startFrame)`，而 `skipForward` 只看 `startFrame` 是否被覆盖 → 续算时两者错位
- **修法**：阶段 2 改为从 `manifest.missingRanges()` 驱动

### Bug C：完整缓存再次分离会清空数据
- **现象**：`resumable = existing != null && !existing.complete` → 完整缓存时 false → writer `setLength()` 抹掉数据
- **修法**：`resumable` 只看文件存在；`complete` 时跳过整个分离

## 风险 #4 的详细说明

**清理缓存时多轨仍在播**：

- Android 的文件语义：`delete` 只是解除目录项，已 open 的 fd 仍可读
- 所以播放不中断（实测 seek 到 60s 正常，2 Tracks active）
- **但**：切歌或杀进程后，这些 stem 文件就永久没了 —— 回到这首歌需重新分离

**是否要改**：
- 现状（允许删，播放继续）是合理的：用户点「清理缓存」= "我不要这些结果了"
- 若要更严格，可在 `busy || isMultiTrack` 时禁用按钮
- **暂不改** —— 这是用户明确表达意图的操作，不需要额外保护
