## Task 0c — 自动化测试通道 ✅（本阶段最重要的产出）

### 复盘：为什么「点不动」

当时 Agent 的方法栈：`adb shell input tap <x,y>`（坐标取自 accessibility bounds）
+ `ui_state`/`take_screenshot` 回读 + `logcat` 佐证。

**观察到的矛盾：**

| 观察 | 含义 |
|------|------|
| `input tap` 退码 0、无 SecurityException | 事件已注入，非权限问题 |
| 坐标确实落在 clickable 按钮 bounds 内、节点 enabled | 坐标没错 |
| 点击后 UI 未变、**零条我方日志**；而 early-return 分支也会渲染 Error 态 | ⇒ 函数**根本没被调用** |
| 用户**手动点击**生效 | 真人点击可达，应用与 dump 都活着 |
| `keyevent HOME` 后 `mCurrentFocus` 逐字节相同、前后截图**像素一致** | ⇒ **回读拿到的是过期帧** |

**两个候选根因（未做决定性区分）：**
(a) API 25 模拟器上注入的 motion event 未送达 Compose；
(b) IDE 设备视图镜像返回陈旧帧，污染「没反应」的判断。

**结论：坐标注入 + 设备视图回读，不是合格的自动化底座** —— 黑盒、时序脆弱、不可交叉验证。

### 解决方案（三层）

- **Phase A ✅ 应用内自驱动**：ViewModel 把「加载」「分离」各拆成
  `suspend` 内部版 + `launch` 公开版；`runAutoSpike()` 在同一协程内顺序 await 两步，
  不依赖状态回调。触发方式：
  ```
  adb shell am start -n pub.miku.neuralstem/.spike.SpikeActivity --ez auto true
  ```
- **Phase B ⬜ 仪器化测试**（`onNodeWithText(...).performClick()` 语义查找，不用坐标）—— 待做
- **Phase C ✅ 验收铁律**：证据一律走非 UI 通道

  | 证据 | 手段 |
  |------|------|
  | 流程是否跑通 | `adb logcat -s SpikeVm SherpaSpike SherpaSep` |
  | 输出了什么 | `run-as ls` + `adb pull` 后本地校验 WAV 头 |
  | 内存/耗时 | 日志内 PSS / ms 数值 |
  | 前台是谁 | `dumpsys window \| grep mCurrentFocus`（**不用** IDE 设备视图） |

**附带踩坑：** `SpikeActivity` 里写的 `vm.state.observe(this)` 是编译错误
（`StateFlow` 无 `observe`），已改为 ViewModel 内部串联。

> 这套通道在后续 Task 1–3 反复救场（尤其 Task 1 的 VM 生命周期问题、

## Task 0e — 长音频流式改造 ✅

**起因：** 0d 的「全曲实测」直接失败 —— `WavIo.read()` 把 5:14 全曲（27.7M float ≈ 110MB）
往 48MB 堆里灌，`OutOfMemoryError` 于 `WavIo.kt:78`。**整曲驻留内存的架构不成立。**

### 推翻的两个假设（★ 避免重蹲）

1. ~~「sherpa-onnx 内部会分块」~~ **错。** 读上游
   `offline-source-separation-spleeter-impl.h` 确认：整段 STFT → 一个张量
   `{2, num_frames/512, 512, 1024}` → 单次 forward，**源码内没有音频块循环**。
   ⇒ **分块必须由 App 层做**，这就是 `StreamingSeparator` 存在的理由。
2. ~~「块间需要回写已落盘数据」~~ **不需要。** 实际实现把「归一化头先算后顺序写」，
   落盘顺序天然单调，`WavWriter.overwriteAt` 已删除。

### 用实测数据推出的两个硬结论（不是猜的）

```
① N_out = N_in − (N_in mod 1024)    ← 用 0d 数据拟合：1151115−139=1150976 完全吻合
   每次调用末尾最多丢 1 个 hop（1023 帧 ≈ 23.2ms）
② 48MB 堆下块长上限：15s 块峰值≈23.8MB（余量26.5MB）；
   30s≈47.6MB（余量仅2.7MB，加缓冲必 OOM）→ 当时默认块长 30s→15s
```

### 正确性前提（新不变量，违反则直接拒绝而非产出坏音频）

`chunk ≥ 2×overlap` —— 否则 head/body/tail 三区穿插，一帧被 3 块覆盖，归一化失效。
仅在真分块（>1 块）时校验，单块场景不受约束（曾因无条件校验误拒合法短音频，被单测抓出）。

### 结构（新增/改动）

```
spike/WavIo.kt            probe(O(1)) / WavReader(按帧随机读) / WavWriter(回填头部+appendRegion)
                          ⚠️ 旧 WavIo.read()/WavData 已删除——那是 OOM 的源头，留着等于埋雷
spike/StreamingSeparator.kt  分块+交叉淡化+顺序落盘；pending 尾巴仅≈overlap帧(147KB，与总长无关)
spike/SpikeViewModel.kt     probe→create engine→StreamingSeparator.run()，块级进度真接线(F3.2)
```

### 块边界伪影 —— 用了三层判据，教训深刻（★ 方法论）

1. ❌ 第一层「边界 vs 全局 p99.99 跳变」：误报 12/21（电波曲瞬态本来就大）
2. ❌ 第二层「边界 vs 随机窗口 max 跳变」：仍误报 16/21（同一个理由，判据没换药）
3. ✅ 第三层「**能量守恒残差**：淡化区 vs 紧邻非重叠区」：
   `残差RMS(淡化区)/残差RMS(邻区) = 1.19×`，边界残差中位 0.048 vs 随机位置 0.020
   → **无系统性不连续**，边界伪影在可接受范围

> **教训：判断「边界坏没坏」必须用与拼接相关的守恒量，不能用样本级跳变统计** ——
> 音乐瞬态会淹没一切样本级判据。

### 单元测试（新增 2 文件）

- `WavIoStreamingTest`：头部回填字节级校验、分块写=一次性写、往返量化误差、
  `appendRegion` 越界拒绝
- `StreamingSeparatorTest`：与单块参照逐样本一致(<1e-5)、tailLoss≤1 hop、两轨不串音、
  约束 A/B 拒绝、进度单调、**参数暴力扫描 20+ 组合**（证伪了「pending 容量会越界」的担忧）

往返误差上界 `2/32768`（<2 LSB，≈−84 dBFS，不可闻）。**本次不改 PCM 语义**
（改了会使 0d 基线失效），留待 Task 4 评估。

## 附录：UVR-MDX 试跑实录（1GB 环境失败，但查明原因）

**做了什么：**
1. JNI/C-API 扩展 `mode` 参数（0=Spleeter 双模型 / 1=UVR 单模型），
   ViewModel 支持 `--es engine uvr --es uvr_model <file>` 选模型，
   输出目录按引擎分（`stems-spleeter` / `stems-uvr-*`）避免 A/B 互覆
2. 下载官方 release 的 UVR-MDX-NET-Voc_FT(66.8MB) 与 UVR_MDXNET_9482(29.7MB)，
   字节数与 release API 核对一致后推上设备

**实测结果（1GB RAM 模拟器，arm64）：**

| 配置 | 结果 |
|---|---|
| Voc_FT + 15s 块 + 4线程 | 首块推理中进程被杀（无 tombstone，静默） |
| Voc_FT + 5s 块 + 2线程 | 同样死 |
| 9482 + 5s 块 + 2线程 | **第一块跑完**(PSS 612MB)，第二块中途死 |

**死亡机制（排除法）：**
- crash buffer 无记录、无 tombstone、无 bad_alloc/abort 日志 → **kernel LMK SIGKILL**
- 死前最后日志 `process done → Resample(第二块) → has died` → 死在第二块推理中
- PSS 612MB 已贴近整机物理上限（1GB，可用 754MB）

**为什么 UVR 比 Spleeter 吃内存（从模型元数据算出）：**
```
MDX-Net: dim_c=4, dim_t=256, dim_f=3072, n_fft=6144, hop=1024
单次 forward 输入张量 = 4×256×3072×4B ≈ 12.6MB
模型内部 chunk ≈ (dim_t-1)×hop = 255×1024 ≈ 5.92s
→ 6G 环境复测（Task 0g）修正了当时的推断：激活**随块长线性涨**，
  15s 块 RSS 冲到 5.8GB 被杀 —— App 层块长必须 ≤ 模型内部 chunk
```

**结论：1GB 模拟器上不可行 —— 是环境限制不是代码 bug。**
- 6G 重测后：UVR 三模型全部跑通（但慢 10–20 倍，见 Task 0g 数据表）
- **真机（≥3GB）复核仍在待办**；管线侧已全部就绪，push 模型即可

> **教训：** 「官方 CI 能跑」≠「低内存设备能跑」。新模型必须先小步验证内存。

## 实测踩坑与修复（全部真机复现 + 验证）

1. **`file://` 直读 `/sdcard/Music` → EACCES**：targetSdk37 无存储权限，属预期。
   自动化测试改用应用自身外部目录文件（应用有读写权）
2. **`by lazy` VM + Activity 重建 → 播放器被杀/状态丢**：

3. **`am start` 相同组件 ≠ 重建**：standard 模式下会**新建实例压栈**
   （旧实例 `isFinishing=true`）；模拟重建要用 **rotation settings**（`user_rotation`），
   不是重复 `am start`

# Task 2 — 波形渲染与拖动跳转 ✅

**对应 guide**：F1.1（渲染）/ F1.2（拖动跳转）/ F1.3（进度指示）

## 代码结构

```
player/WaveformExtractor.kt  振幅包络提取:每秒 50 点(5:14 歌≈15000点≈120KB);
```

## ★ 选型变更（guide §八.1 留档）：media3 Extractor → 平台 MediaExtractor+MediaCodec

- 初版计划：手写 media3 `TrackOutput` 实现，直接驱动 Extractor 拿 PCM
- 撞坑：`sampleData` 有 **2/3/4 参三套重载**（2 参 default、3 参 abstract、4 参 abstract），
  Kotlin override 期间反复报「does not implement / overrides nothing」，

- 根因分析：media3 unstable API 的接口继承在 Kotlin 里成本极高（多重载 + 版本演化）；

  即便绕过 override 问题，管线还是绕不开 MediaCodec
- **解法**：直接用**平台 MediaExtractor+MediaCodec**（API21+ 全支持）：
  顺带把波形支持从「仅 wav」扩展到**全格式**，且系统类在 Kotlin 继承里零兼容烦恼

> **教训**：选型先看「哪个 API 的 Kotlin 继承成本低」—— 系统框架类通常比
> unstable 的 AndroidX 类更稳；**绕不开 MediaCodec 时就别绕，直接一步到位**。

**波形数据量：**
- 每秒 50 包络点（与采样率无关）：5min 歌 = 15000 点 × 2 × 4B ≈ 120KB
- 柱宽自适应：点数多于像素宽度时自然密集成「实心波形」，无需降采样逻辑
- 包络高度按全局峰值归一化（留 8% 边距），避免单点爆音把其余波形压扁

**拖动体验：**

**双轨预埋（Task 4）：**
- `WaveformView(waveforms: List<WaveformData?>)` —— Task 2 传单轨；
  Task 4 喂 vocals/accompaniment 两条即自动叠加，`trackColors` 循环取色，

- 附注：`ExoPlayer.Builder` 根本没有 `setAudioSink` 方法

> **教训**：AndroidX 的 Builder 链经常在版本间变动，**先 javap 看真实 API 再写代码**，
> 省一轮试错。

## 音高换算（关键细节）

- `playbackParameters.pitch` 的单位是**线性倍率**，不是半音

- 验证：+12 半音 = 2.0x（八度）、−12 = 0.5x、+7 = 1.4983（纯五度）—— 单测已盖


## Task 4 — 分离接入主流程（已完成）

**动机**：盘点发现的最大产品断裂 —— 播放侧支持全格式（mp3/flac/aac），
分离侧只认 WAV+PCM16+44.1kHz；能播的歌不能分离，分离完的 stem 也回不到播放器。

### 4.1 分离输入格式扩展 ✅

**架构改动：`StreamingSeparator` 从具体 `WavReader` 抽象为 `FrameSource` 接口**

```
spike/FrameSource.kt（新增）
├── interface FrameSource           channels/sampleRate/totalFrames/readFrames
├── WavFrameSource                  包装 WavReader（WAV@44.1k 流式直读，零驻留）
├── MemoryFrameSource               已解码 PCM 按帧切片（压缩格式走这条）
├── Resampler                       线性插值；同采样率零拷贝短路
└── SeparationInput                 统一入口：open() / probe()
```

**分支策略（`SeparationInput.open`）：**
| 输入 | 路径 | 内存 |
|---|---|---|
| wav @44.1k | `WavFrameSource` 流式直读 | 与文件长无关 |
| wav @其他采样率 | 解码 → 重采样 | 整曲 PCM |
| mp3/flac/aac/m4a | 解码 → 重采样 | 整曲 PCM |

**声道归一化**：单声道复制成立体声、多声道取前两声道（模型契约要 stereo）。
**重采样**：`rate = dstRate/srcRate`，线性插值；44.1k 输入零损失零开销。

**真机实测（BF00A / Android 16 / 12GB / arm64）：**
```

SepInput: decoded: frames=6640128 ch=2 sr=44100              ← MediaCodec 解码
StreamingSep: 6 chunks, chunk=1323000 (30s块)
streaming done: in=6640128 out=6639576 tailLoss=552
separation done: infer=19258ms audio=150569ms realtime=7.82x peakPss=753.6MB
```

### 真机暴露的 3 个 bug（均已修）

1. **`MediaFormat.KEY_PCM_ENCODING` 缺失 → NPE**

### 4.2 分离任务后台化 + 结果缓存 ✅

**新增 `SeparationRepository`（进程级单例）**

为什么必须独立于 ViewModel：分离是 30s–几分钟的长任务，
绑在 `SpikeActivity` 的 ViewModel 上会被 `onCleared()` 打断，

## V1 — 多轨 seek 对齐的波形级验证 ✅

**背景**：guide §3.6 硬要求「seek 后各轨必须严格对齐，不能出现可感知的相位偏差」。
Task 4.4 的 `MultiTrackController` 只有**逻辑保证**（同帧下发 + 共享 PlaybackParameters），
从未实测。本项用**双重证据**钉死：离线互相关（主）+ 真机 dumpsys（辅）。

### 证据一：离线互相关（离线，确定性，主证据）

用**真机缓存的真实分离产物**（两组、共 4 个 wav）做逐样本互相关：

| 素材 | 时长 | 全局扫描窗数 | lag 分布 | 结论 |
|---|---|---|---|---|
| stemsA（`8faa499b…`） | 150.56s | 28（1s 窗 / 5s 步长，±200 采样点） | **{0: 28}** | 零偏移 ✅ |
| stemsB（`d3ef7e49…`） | 195.49s | 29（+3 个低相干窗跳过） | **{0: 29}** | 零偏移 ✅ |

→ **判定窗共 57 个，最大 \|lag\| = 0 采样点 = 0.0000 ms**。判据 `\|lag\| ≤ 1 采样点` 通过。

**阳性对照**（验证判据本身没坏）：注入已知偏移 +1 / +37 / −123 帧 → 全部正确检出。

### ★ 方法论踩坑（两次错误判据，均为「负结果实验」的教训）

1. **首次扫描报「FAIL max\|lag\|=200」** —— 诊断后发现：尾部最后 1 个窗
   （149.56s）的**两轨 RMS 均为 0.0000**（尾部静音，即 `tailLoss` 区）。
   静音互相关无意义，峰值会贴到搜索边界（`-200/-2000/-10000` 随 `max_lag` 变）——
   **是搜索边界伪影，不是错位**。
2. **第二次报 stemsB 有一个窗 lag=−191** —— 定位后发现该窗
   `RMS_v=590 而 RMS_a=14169`：人声近乎静音（纯器乐段），**两轨无共享信号**，
   互相关被噪声主宰。同样贴边界。
   → **修正判据**：只在「两轨都有实质能量」的窗上判 lag（跳过无共享信号的窗）。

> **教训（与 0e 的「边界伪影」一脉相承）**：互相关延迟估计要求
> **两轨共享一个可辨识的信号成分**。在静音/低相干区做互相关，
> 得到的必然是无意义的边界值。**判据必须先保证可观测性，再谈数值**。

## V2 — guide N4 后台播放（MediaSessionService + 媒体通知）✅

**背景**：调研发现 N4 从未实现（见上文本轮新发现）。本轮补齐。

### 架构（遵循 Media3 官方 background-playback 模式）

```
player/PlaybackService.kt  [新增]  MediaSessionService
  ├── onCreate: 建唯一 ExoPlayer + MediaSession.Builder
  ├── onGetSession: 返回该 session
  ├── onTaskRemoved: 未播放时 stopSelf（播放中则默认继续）
  └── onDestroy: player.release() + session.release()
```

**关键决策：player 的所有权从 VM 移到 Service**

| 项 | 改前 | 改后 |
|---|---|---|
| 单轨 player 拥有者 | `PlayerViewModel`（`ExoPlayer.Builder`） | `PlaybackService` |
| VM 如何控制 | 直接持有 `ExoPlayer` | `MediaController`（异步连接 session） |
| 生命周期 | 跟 VM（Activity 级） | 跟 Service（进程级，后台存活） |
| `PlayerViewModel.player` 类型 | `ExoPlayer` | `Player?`（MediaController 实现 Player） |

选 `MediaController` 而非直接共享 ExoPlayer 的理由：这是官方推荐路径，
且 Controller 能同时给**系统媒体控制/通知广播/蓝牙**用（无障碍）；
VM 用到的 API（`playbackParameters/addListener/seekTo/duration/isPlaying`）
在 `MediaController` 上都有，调用点几乎零改动。

**多轨与 N4 的边界**：本 Service 持有的是**单轨主播放器**；
多轨（`MultiTrackController`）仍归 VM（复用 4.2 的「进程级存活」思路）。
本轮 N4 聚焦 guide 明确要求的「单轨播放的后台延续 + 通知」。

### ★ 真机暴露的 bug：MediaController 异步连接竞态（已修）

logcat 实录（首次部署）：
```
PlayerVm: VM init
PlayerVm: loadAndPlay: test.mp3
PlayerVm: loadAndPlay ignored: controller not connected yet   ← ❌ 载入被静默丢弃
PlaybackService: service created, session ready
PlayerVm: MediaController connected to PlaybackService       ← 118ms 后才连上
```

- **根因**：`MediaController` 是**异步**连接的（实测 ~120ms）；
  而 SAF 导入 / `auto_play` 入口可能在 `onCreate` 里就立即调 `loadAndPlay`，
  此时 `controller` 还是 null → 请求被丢弃。
- **解法**：新增 `pendingLoad: (Player) -> Unit`，连接未就绪时暂存，
  连接回调里重放（`doLoad`）。
- **复验**：`loadAndPlay queued` → `connected` → `doLoad` 三步齐全，播放成功。

### ★★ V4.2 重大发现：后台运行会触发 CPU cgroup 降频（~2× 变慢）

同一个 4 分钟 wav，**前台** vs **后台**：

| 场景 | infer | realtime | 依据 |
|---|---|---|---|

**根因（已取证）**：应用不在前台时，Android 把它放入 `/background` cgroup：
```

3:cpuset:/background
2:cpu:/background
1:blkio:/background
# cat /proc/<pid>/oom_score_adj
900           ← 后台优先级极低
```

**影响（重要）**：
- **分离耗时对“应用是否前台”高度敏感**，后台可能超过 guide 的 60s 门槛。
- 因此，报告/验收的性能数据**必须注明“前台运行”**，否则不可复现。
- N5（不中断）与性能目标存在张力：若要求后台也 ≤60s，
  分离任务应像播放一样用**前台服务**（当前仅播放用了）。
  —— 这一条建议列入后续改进（非本轮阻塞项）。

| C API | ✅ 结构上是通用的 | `stems[] + num_stems` + `GetNumberOfStems()` |
| 转换脚本 | ❌ 硬编码 2 | `export_onnx.py`: `"stems": 2` |
| Spleeter 运行时 | ❌ 硬编码 2 | `resize(2)` + `RunVocals/RunAccompaniment` + 二路掩码 |
| UVR 运行时 | ❌ 硬编码 2 | `resize(2)`，non-vocals = 源−vocals |
| 官方 release | ❌ 无 4-stem 模型 | 25 个资产全是 2-stem |

### ★ 但找到了现成的 4-stem ONNX

**`Best-Practice/spleeter-4stems-onnx`（HuggingFace，Apache-2.0）**：
- vocals / drums / bass / other —— 四个独立 U-Net（9,826,759 参数/个）
- fp16：**19.7MB/个**（共 79MB）；fp32：39.4MB/个；**自包含**
- 作者自验：`sum(4 stems) − mix = −153.1 dB`；30s 四路推理 **1.69s（~18× 实时，CPU）**
- **接口**：`x/y : float32 [2, num_splits, 512, 1024]`（幅度进、幅度出）；
  STFT = **periodic Hann / 4096 / hop 1024**；软比例掩码 `mask_s = (e_s² + 1e-10/4) / Σe_s²`；
  频带扩展用 `average`（不用 `zeros`，后者 −23dB 高频洞）

> ⚠️ **ELU 陷阱**：4stems 用 **ELU**，2stems 用 LeakyReLU/ReLU，**权重形状完全相同**；
> 用 2stems 实现直接载 4stems 权重会“无报错地返回垃圾”
> （作者实测 max error 945 vs 信号量程 178）。激活值已写进 ONNX metadata。

### 可行性结论

**项目现有的 sherpa AAR 不能直接跑这 4 个 ONNX**：
- AAR 里只有 **`libonnxruntime.so`（C API）**，**没有 Java/Kotlin 的 ORT 绑定**。
- 要跑自己的 ONNX，必须二选一：
  - **(A) 加 `onnxruntime-android` Java 依赖**（干净，需确认版本与已有 so 冲突）
  - **(B) 自己写 JNI 调 AAR 里那份 `libonnxruntime.so` 的 C API**

**还需自建**：① STFT/iSTFT（periodic Hann/4096/hop1024/band ext）；
② 四路调度 + 跨四 stem 软掩码；③ 分块流式（4stems 内存 = 4× 单模型）；
④ JNI/Kotlin/UI 全链路（当前 `SeparationResult`/`MultiTrackController`/UI 都按 2 轨写）。

**工作量估算**：路线 A + 参考 DSP 移植 ≈ **1.5–3 人周**。
**建议**：本轮不做；模型与接口已完全清楚，随时可启动。

## M5 — 方案 B「边分离边播」可行性评估（不实现）✅

**用户设想**：分离只要快于播放，就能切片处理，不必等整曲分离完。

### 结论：**本机上对 Spleeter 成立；对 UVR 不成立**

| 引擎 | 4min 分离 | 播放 | 分离/播放 | B 判定 |
|---|---|---|---|---|
| Spleeter | 30.4s | 240s | 1:7.9 | ✅ |
| UVR 9482 | 240.4s | 240s | 1:1.0 | ❌ 临界 |
| UVR Voc_FT | 707.5s | 240s | 2.9:1 | ❌ |

- Spleeter 下，播放器可在分离开始后**立即开播**，分离点领先播放一段。
- UVR 下**在本机上**分离≈或慢于播放，播放会追到分离点后卡住。

### 实现工作量（本轮只评估）

现状：`MultiTrackController.load()` 收 `Uri` → ExoPlayer 默认文件 DataSource；
`StreamingSeparator` 顺序 append 写 wav，`WavWriter.close()` 才回填 header length
⇒ 分离中的文件 header 非法，不能播。

| 路径 | 做法 | 工作量/风险 |
|---|---|---|
| **B1 自定义 DataSource** | 传一个能播“已分离前缀”的 DataSource；边写边通知可读长度 | 中（最干净）|
| B2 分片文件 | 每块落独立 wav，播完换片 | 中高（切点易爆音）|
| B3 预写超大 header | 先写足够大的 length，持续 append | 低（需实测 WAV Extractor）|

**推荐 B1**；估工作量 **约 3–5 天**。

### 本轮决定

**不实现**（Q4=甲）。理由：
1. 它是**体验优化**，不是功能缺口 —— 现有“先分离后播放”已经能用；
2. 收益主要在“长篇等待”时才明显（本机上 Spleeter 已经够快）；
3. 若未来引入 UVR 作为可选引擎，B **在部分设备上可能不可用**，需回退“先分离后播放”。

**若后续要做**：优先 B1；且先确定“默认引擎”策略。

## T2 — 单↔多轨切换 ✅（★ 抓到并修复一个真 bug）

**自动化入口（新增）**：`--ei mt_exit_after <ms>` —— 载入多轨后 N ms 自动退出（非 UI 通道）。

**第一次实测（修复前）**：
```
MtSwitch: triggering exitMultiTrack after 6000ms
PlaybackService: exitMultiTrack(v2) → 单轨
（❌ 无 attachSingleEq —— EQ 未重挂）
```
**根因**：`handleExit` 里写了
`singlePlayer?.let { if (it.playbackState == Player.STATE_READY) attachSingleEq(it) }`
—— 退出时主轨刚从多轨下停下，**不是 READY** → 条件不满足 → **EQ 漏挂**。

**修复**：去掉 `STATE_READY` 门槛，无条件调 `attachSingleEq`
（它自身会判 `audioSessionId != 0`）。

**修复后实测**：
```
exitMultiTrack → attachSingleEq: audioSessionId=11137
AudioEq: Equalizer attached: session=11137 bands=5
EqCtl: attach(single, session=11137) available=true
```
✆ **退出多轨后 EQ 正确重挂**。

> **教训**：与坑 42/43 同一族 —— **会话重建后必须重挂 EQ，且不能用“READY”做门槛**
> （主轨从多轨退出时不处于 READY）。新增坑 47。

## S1 — 多轨 seek 后的对齐 ✅（**不需要推翻架构**）

**背景**：外部调研质疑“多实例方案 seek 后几乎必然跑偏，必须改单实例混音”。

**方法**：新增诊断命令 `CMD_DEBUG_POS`（日志打印每轨 `currentPosition`）
+ 自动化 `--ez mt_pos_probe true`。

### 决定性证据（seek 后立即暂停，读每轨 `currentPosition`）

```

POS_MAIN(vocals)     = 10000
POS_TRACK[1](accomp) = 10000    ← 2/2 次运行精确一致（0ms 差）
```

### 播放中的 ~200ms 差 = **估计伪影**，不是真实错位

| 观测 | 值 |
|---|---|
| 无 seek、多次暂停读数 | **46ms → 2ms**（随机变，符号也翻）|
| seek 后播放中 | ~200ms |
| seek 后立即暂停 | **0ms** |
| 输出线程 | 两轨在**同一 MixerThread**（`AudioOut_15`），帧级混音 |
| 欠载 | `Underruns=0` |

## S2 落地 — Demucs 速度优化尝试（Gen3）

### ★ 阶段耗时分解（40s / 7 块，threads=4）

| 阶段 | 耗时 | 占比 |
|---|---|---|
| read | 90 ms | 0.2% |
| STFT | 1377 ms | 3.7% |
| **model（ORT）** | **26701 ms** | **70.7%** |
| **iSTFT** | **8233 ms** | **21.8%** |
| accum | 311 ms | 0.8% |

### 优化 1：线程数扫描（针对 70% 的 model）

| threads | inferMs（40s）| 备注 |
|---|---|---|
| 4 | 38.5s | |
| **6** | **32.3–35.5s** | ✅ 最快 |
| 8 | 46.7–51.2s | ❌ **超订**（大小核 + 系统争抢）|

⇒ **默认改 6**。Gen3 是**大小核**（1×X4+3×A720+4×A520），8 线程会调度到小核 → 反而慢。

### 优化 2：FFT twiddle 预计算（针对 22% 的 iSTFT）

`Fft4096.fft` 原先每级重算 `cos/sin`。改为**预计算 twiddle 表**（按 `len` 缓存）。
⇒ iSTFT **8400 → 7100–8100 ms**（约 **10–15%**）。单测仍全绿。

### 优化 3：NNAPI 执行提供者（❌ 不可用）

sherpa 的 ORT **导出了 `OrtSessionOptionsAppendExecutionProvider_Nnapi`**，
且 htdemucs 图 **82% 算子被 NNAPI 接受**（1513 节点中 1246 个）。
但实测：
```
number of partitions supported by NNAPI: 131   ← 图被切成 131 片
```
**131 个分区** ⇒ 大量 CPU↔NPU 数据搬运；同一 40s 音频 **130s+ 仍未跑完**
（CPU 仅 33s）。 ⇒ **NNAPI 对本模型不可用**（已加开关但默认关）。

### 优化后总结

| 版本 | model | istft | total（40s）|
|---|---|---|---|
| 原始（threads=4）| 26.7s | 8.4s | ~38s |
| **优化后（threads=6 + twiddle）** | ~22–24s | ~7.1–8.1s | **~30–34s** |

⇒ 净提升 **~15–20%**。模型推理（~70%）是 **ORT CPU 硬骨头，无 GPU/NPU 可吃**，
在不换运行时的前提下已接近上限。

### 优化 4：内存诊断（❌ 无旋钮可调）

**空载 PSS = 137 MB → Demucs 运行峰值 5045 MB（+4.9GB）**。

诊断思路（排除我方代码）：
| 实验 | 结果 |
|---|---|
| 8s（2 块） vs 40s（7 块） | PSS **5019 vs 5045 MB** ⇒ **与块数无关**（非累积泄漏）|
| 去掉每源 `copyOfRange` | 无变化 |
| `session.use_env_allocators=0` | **无变化** |
| `arena_extend_strategy=kSameAsRequested` | **无变化** |

⇒ **这 ~4.9GB 是 ORT 跑 htdemucs 大激活张量的固有 CPU arena 开销**，
无会话级旋钮可调（且 sherpa 那份 ORT 符号隐藏，无法窥探内部）。
**判断：这是“必要”开销**（除非换运行时 / 减小窗）。Gen3 16GB 上可接受，
中端 12GB 上偏紧。⇒ 接受现状，不硬攻。

### ★ 优化 5：iSTFT 并行化（收益最大的一步）

iSTFT 的 4 个 stem **互相独立**（各自 specStem/time，accum 写入各 src 不相交），
→ 用 4 线程池并行（`Executors.newFixedThreadPool(4)` + `submit`/`get`）。
前置修复：`Fft4096` 的 twiddle 改为 **init 时一次性预计算**（原 `HashMap.getOrPut` 非线程安全）。

**效果（40s）：** iSTFT **~8200ms → 2085ms**（快 ~4×，近理想加速）。

**正确性**：逐样本 NCC（旧串行 vs 新并行）= **1.000000**（4 轨全部）。

### ★ 优化累计（40s 音频，Gen3）

| 版本 | infer | 实时 |
|---|---|---|
| 原始（threads=4）| 38.5s | 1.04× |
| +线程 6 | 32.2s | 1.24× |
| **+iSTFT 并行** | **29.6s** | **1.35×** |

⇒ 净提升 **~23%**。此时 `model=25.3s` 占 **85%** —— 已彻底触到 ORT CPU 天花板。

### ★ 优化 6：同样手法用于 Spleeter 4-stem（收益更大）

`Spleeter4Separator` 的 mask+iSTFT 也按 stem 并行（进程级共享 4 线程池）。

| | 优化前 | 优化后 |
|---|---|---|
| 120s 总推理 | 32724 ms | **17320 ms** |
| 实时 | 3.67× | **6.93×** |

⇒ **快 ~1.9×**（Spleeter 的 mask+iSTFT 占比更大，收益更明显）。
正确性：`sum(4)−mix = −69.9 dB` ✅（判据 −60dB 级）。

### ★ 全部优化汇总

| 引擎 | 设备 | 优化前 | 优化后 |
|---|---|---|---|
| Demucs（40s）| Gen3 | 38.5s（1.04×）| **29.6s（1.35×）** |
| Spleeter 4-stem（120s）| Gen3 | 32.7s（3.67×）| **17.3s（6.93×）** |

手段：**线程 6 + FFT twiddle 预计算 + iSTFT 按 stem 并行**。均无运行时/兼容性风险。

### GPU/ExecuTorch 路线评估（已核实，暂不做）

**核心障碍**：sherpa 那份 ORT **只导出 2 个 EP**（一手取证）：
```
OrtSessionOptionsAppendExecutionProvider_CPU
OrtSessionOptionsAppendExecutionProvider_Nnapi
```
（字符串里的 CUDA/DML 只是编译残留的**错误消息**，符号未导出 → 不可用。）
⇒ **给现有 ONNX 模型加 GPU，必须先解开“坑 49 的符号死结”**（需重构分离层或新运行时）。

| 方案 | 只对哪些模型生效 | 预估收益 | 兼容性风险 |
|---|---|---|---|
| ORT + NNAPI | 全部 | ❌ Demucs 实测无效（131 分区）；4-stem 待测 | 中 |
| ORT + XNNPACK | 全部 | 1.2–1.8×（模型部分）| 低（但碰符号冲突）|
| ORT + QNN | 全部 | 3–8×（若算子全支持）| 高（强绑骁龙）|
| **ExecuTorch+Vulkan** | **只 Demucs**（只有它有现成 `.pte`）| 2–5×（乐观）| 高 |

**Amdahl 关键**：即便模型 3×，总时间也只 ~1.7×（因 iSTFT 占 22% 且不受益）。
⇒ **暂不做 GPU 重写**，留作报告“未来工作”；**待补一个最小上限实验**（用 Maven ORT 单独跑 htdemucs 量 XNNPACK 实际收益，即使绕开本项目）。

### ★★ GPU/NPU 上限验证实验（已完成，实测）

**方法**：新建独立 `:bench` 模块（`bench/`，**不引 sherpa**，单独 APK），依赖
`com.microsoft.onnxruntime:onnxruntime-android-qnn:1.29.0`，用 Java API 加载同一个
`htdemucs_embedded.onnx`，逐 EP 跑同一 7.8s 窗（预热后 3 次取中位）。

**实测（Gen3）：**
```
ORT 1.29.0, available providers = [CPU, QNN]
EP=CPU     OK  median=4237ms  → 1.84× 实时
EP=NNAPI   FAIL  "This binary was not compiled with NNAPI support"
EP=XNNPACK FAIL  "XNNPACK execution provider is not supported in this build"
EP=QNN     OK  median=3290ms  → 2.37× 实时   ← 骁龙 NPU
```

| EP | 中位 | 实时 | vs CPU |
|---|---|---|---|
| CPU（ORT 1.29.0）| 4237 ms | 1.84× | 基线 |
| **QNN（骁龙 NPU）** | **3290 ms** | **2.37×** | **1.29×** |
| NNAPI | ❌ 未编入 | — | — |
| XNNPACK | ❌ 未编入 | — | — |

**结论（报告可直接引用）：**
1. **骁龙 NPU（QNN）实测只有 ~1.3×** —— 远低于乐观预期（3–8×）。
   原因：htdemucs 含大量**非标准算子回退 CPU**，QNN 只吃 conv/gemm；
   加上 CPU↔NPU 数据搬运。
2. **XNNPACK / NNAPI 在所有 Maven ORT 包里都未编入**（Java API 有方法名但底层不支持；
   官方“带 XNNPACK 的包”需 `--use_xnnpack` 自编译，非现成 artifact）。
3. **CPU 基线各 ORT 版本基本一致**（同源代码；1.29.0=4237ms vs sherpa 1.28.2≈4200ms/块）。
⇒ **实测坐实了“不值得为 GPU/NPU 重构”**：上限仅 ~1.3×，且换 EP 还要解开
坑 49 的符号死结（重构分离层）。 **结论与 .critical_steps 一致：不做。**

## 转盘语义（★ 定稿，经多轮讨论）

**三环同心**（顺时针方向与真唱片一致）：

| 环 | 是否转 | 内容 | 交互 |
|---|---|---|---|
| **① 外环** | **不转** | **整曲波形** + 已播/未播分色 | 点/拖 = seek |
| **② 中环** | **不自转**（波形随播放滚动）| **局部波形**：唱臂两侧的时间窗 | — |
| **③ 内圈** | **匀速自转** | 封面（裁圆）/ 无则**曲名环** | 点 = 播放/暂停 |

**中环几何（定稿）**：
- **唱臂固定在 2 点方向**（= 当前进度锚点）；**分界线 9 点**；
- 角度分配：**过去 165° / 未来 180° / 扇形遮罩 15°（7点半→8点）**；
- “未来多放”（未播看得多）。

**转速语义（定稿）**：
- **基准一圈时长 = `secPerTurn` 秒**（设置可调，**默认 18**，范围 **9–36**，**step 3**）；
- **实际一圈 = secPerTurn ÷ speed**（2.0×→9s，0.5×→36s）；暂停停转；
- ⇒ “转速”有物理意义（一圏=具体秒数），且 18s 整数、封面可读。

> ⚠️ 方向：真唱片**顺时针**；实现上 `rotation += 正值` 在屏幕坐标下即顺时针（已验证）。

## ★ “松手闪”根因（官方调研后的正解）

经过反复试错仍未消除 seek 闪 → **读官方 Compose 性能文档**得正解：

> 官方最佳实践：「Defer reads as long as possible」——
> **当频繁变化的状态传给 modifier/子组件时，用 lambda provider，让读取发生在
> layout/draw 阶段**，从而跳过 composition。
> “如果你仅仅为了 re-layout/re-draw 而触发重组，就该警觉。”

**本项目根因**：`PlayerScreen` 把 `positionMs/durationMs` 作为**参数**层层往下传
（`DeckView(positionMs=...)` / `ProgressBar(positionMs=...)`）→ 每次进度/seek 变化
→ **整条链路重组** → 视觉“闪”。另外 `seekTo()` 曾写 `_state.value=...copy(positionMs=)`
→ 整页重组。

**正解（已实施）**：
1. 新增 **独立 `progressFlow`**（position/duration），seek/轮询只写它；
2. `DeckView` / `ProgressBar` 的参数改为 **`positionProvider: () -> Long`**（lambda），
   在 **Canvas draw 阶段**才读 → 进度变化只**重绘**，不重组。
3. `seekTo()` 不再写大 state。

> 另：官方还指出 **“backwards write”（在 composition 中写已读过的 state）会导致每帧
> 无限重组** —— 我们的 `EqPanel` 有 `if(!dragging){localDb=snapshotDb}` 属此类，需警惕。

## ★★ “闪”的真正根因（已定位并修复）

用户反馈：“**导入/分离不闪，下面的全部闪**”。这个现象是**决定性线索**：

- “导入/分离”按钮在 `if (state.isReady)` **之外**，所以不闪；
- 其余全部内容在 `if (state.isReady)` **之内**，所以全闪。

⇒ **`isReady` 在“闪”**！

**链路**：
1. `isReady = (playbackState == STATE_READY)`；
2. **seek / 缓存不足时 ExoPlayer 会经历 `READY → BUFFERING → READY`**；
3. `BUFFERING` 那一下把 `isReady` 置 `false` → **`if (state.isReady)` 整块 UI 被移除**；
4. 回到 `READY` → 又重建 → **可见闪烁**。

**修法（已实施）**：`isReady` 改**latch（一次性置位）**：
```kotlin
val newReady = when (playbackState) {
    Player.STATE_IDLE -> false           // 仅停止/错误才清
    else -> cur.isReady || ready         // 一旦 READY 就保持（BUFFERING 不再清）
}
```
并在 `doLoad`（新歌）时重置 `isReady=false`。

> 教训：**“内容开关”变量不能直接绑定到“瞬时状态”（如 STATE_READY）**；
> 否则任何瞬时波动（缓冲/seek）都会让整块 UI 消失重建。应使用 **latch / 派生稳定值**。

## ★★★ 实测：重组计数（用数据终结“闪”的猜测）

手段：临时 inline 重组计数器（子 composable 会被 skip，不可靠）。

| 场景 | `PlayerScreen` 重组 | `ProgressBar` 重组 |
|---|---|---|
| 播放 8s | **1 次** | 5 次/秒（=200ms 轮询，**预期**）|
| 点 +10s ×3 | 1 → 5（≈1.3/seek）| — |

⇒ 架构已正确：**整页不再随进度重组**，只有进度条局部重组。

### 顺带修的两个真 bug（都影响功能）

1. **`StateFlow.value` 不是 Compose State**：
   我一开始把进度条改成 `positionProvider = { vm.progress.value.positionMs }`，
   但 `StateFlow.value` **不是 Compose 可观察对象** → 读它**不触发重组** →
   时间永远显示 `0:00`。正确做法：先 `collectAsState()` 得到 Compose `State`，
   再在 lambda 里读它（读发生在子组件/draw 阶段 → “隔离重组” + “可观察”兼顾）。
2. **seek 时 `p.duration` 短暂为 0/UNSET**：`onPlaybackStateChanged` 里把它写成 `0`
   → 多余重组（≈2/seek）。修：仅在 `dur > 0` 时覆盖。
3. **`detectDragGestures` 需要 `change.consume()`**：否则手势被父级抢走 → “拖不动”。

### 已用的“高级”Compose 手法（汇总）

| 手法 | 用途 |
|---|---|
| **lambda state provider**（`positionProvider: () -> Long`）| 推迟状态读取到 draw 阶段，跳过 composition |
| **latch 化瞬时状态** | 防止“内容开关”随缓冲/seek 抖动 |
| **guard 写入**（值未变不写 state）| 减少无效重组 |
| **独立 `progressFlow`** | 高频进度与大 state 解耦 |
| **波形抽稀 + 窗口遍历** | 控制每帧绘制量（防卡/ANR） |

### ★ R3 迭代 3：“卡”的真根因 = 进度 collect 在页面层

**用户关键线索**：“卡”与**进度条的已播放时间显示一起卡**。

**定位**：`PlayerViewModel` 轮询（主线程、100ms）经日志实测**稳定**
（`POLL/s=10 maxGap~105ms`，无阻塞）⇒ 不在“进度更新频率”。而在**每 100ms 变化时触发的重组**：
`PlayerScreen` 顶层 `val progressState = vm.progressFlow.collectAsState()`
→ **每 100ms 重组整个播放页（含 DeckView）** → “时间 + 转盘一起卡”。

**修法**：进度流**不在页面层 collect**；改为**传给 DeckView / ProgressBar，各子组件内部 collect**
（重组范围限于该子组件），且 **DeckView 仅在 draw 阶段读**。
实测 `gfxinfo` 50th：**26ms → 12ms**（参考值，仪器测量不完全可靠）。

**教训**：**高频状态（~10Hz）的 collect 位置决定重组范围**——放在页面顶层会把整页拖下水；
尽量放到“叶子”组件、或仅在 draw 阶段读。

### ★★ R3 迭代 4：进度“卡/跳/回弹”的**最终根因与实现**（真机验证通过）

**现象（多轮迭代后）**：
- 播放中**数字（已播时间）+ 转盘内环 + 中环波形**持续性“卡/跳”；
- **1 倍速下开头 ~3-4s 回弹一下**（加速则推迟）；
- **声音不卡**（音频独立线程，UI 才卡）。

**★ 根因（实测数据确证，见 investigation 小节）**：
`Player.currentPosition` 报告**不均且会“停滞”**：
- 正常时增量 ~= 轮询间隔（100ms），但**带 ~183ms 的固定滞后**；
- **周期性停滞 ~300–800ms（读同一值），然后一次“补跳”到位**（AudioTrack 播放头更新的粒度）。
  - 实测序列：`...100,100,108,...`；异常点 `+338/+348/+314`（小跳）；偶发 `-762`（回退）；
    更关键的一段：`pos=2950` **停滞 7 个采样（~700ms）**，drift 从 183 一路涨到 795，最后跳到 `3004`。

**两个叠加的故障机理**：
1. **停滞（~800ms）使“外推 vs 真实”的 drift 超阈** → 触发**重锚** → 锚点被硬拉到真实值 → **一次性跳**。
2. 重锚往往**连续几帧触发**，平滑层（`SmoothPosition`）**累加**这些捕获量 → **过度补偿 → 回弹**。

**★ 实现（最终方案）**：
- **UI 时钟锚点（`PlayerViewModel.UiClock` + `anchorFlow`）**：
  `pos(now) = positionMs + (now − realtimeMs) × speed`；轮询里**仅在必要时重锚**
  （首帧 / 暂停 / 变速 / duration 变 / 漂移超阈）。
- **重锚阈值 `ANCHOR_DRIFT_TOLERANCE_MS = 1800ms`**（> 停滞幅度）：
  ⇒ 停滞期间**不重锚**（声音仍在播，外推“领先”反而更接近真实）；且需**连续两次**超阈才重锚（抑单点尖刺）；
  离群采样（与预期增量偏差 >2.5×）**不参与重锚**。
- **平滑层 `player/SmoothPosition.kt::rememberSmoothPosition(anchorFlow)`**（UI 侧：`DeckView` + `ProgressBar` 共用）：
  每帧 `disp = anchor.extrapolate(now) + delta`；当锚点**实质变化**（`positionMs`/速度/播放态变，**不含 `realtimeMs`**）
  时把“显示值与新外推的差”计入 `delta`，再**逐帧衰减**（`×0.85`）→ 把突变摊成 ~0.4s 过渡。
  **捕获冷却 300ms 内“替换而非累加”**（避免连续重锚过度补偿）。
- **进度 collect 位置**：不在 `PlayerScreen` 顶层，改为 **`DeckView`/`ProgressBar` 内部 collect**，
  且**仅在 draw 阶段读**（避免每 100ms 重组整页）。
- **转盘内环转角**：由 `positionMs` 直算（`positionMs/turnMs×360°`），与中环、数字**同源**。

**★ 效果（真机）**：
- 开头 14s 内 `[ANCHOR]` **仅 5 次 force（启动期）**，之后**再无重锚**；`SmoothPos` **零 capture**（无跳变）；
- 用户确认：“好像好了”（数字/转盘平滑，无回弹）。

**★ 排查链（教训）**：
1. 先后错判为：AudioSink 超时 → StuckPlayerDetector → 每帧重组（rotation state）→ collect 位置；
   **每一步都用实测（logcat / gfxinfo / dumpsys）推翻或印证**，不靠猜。
2. **`gfxinfo` 的 “50th percentile”是“每帧 UI 耗时”，非帧间隔**；`Janky=0` 时不能凭它断言“卡”。
3. **`currentPosition` 不可直接信任**：需“**锚点外推（本地时钟）+ 平滑捕获（缓追）+ 容忍停滞（大阈值）**”三层。

## ★ 歌单/切歌 打通（队列化）

**动机**：导入用 `setMediaItem`（只替换单曲）→ 播放器永远 1 首 → 滑盘切不了、歌单与播放器脱节。

**核心不变量**：**当前歌单 = 播放队列**；单轨播放的曲必须属于当前歌单；歌单顺序 = 播放顺序。

### 定稿契约（用户逐条确认）
- **两类歌单**：`FILE`（手动加、**可排序**）/ `FOLDER`（随外部文件夹、**不可排序**）。
- **默认歌单**：`id="default"`、`isDefault=true`、**不可删 / 可清空 / 不改名**。
- **添加**：文件歌单 → 插到“当前曲之后”；文件夹歌单遇外部导入 → **切回默认歌单** → 插当前曲之后 → 播新的。
- **去重**：同一 uri 已在歌单 → 不重复加，定位到它。
- **末尾行为**：**默认循环（`REPEAT_MODE_ALL`）**；设置可改**停止（`OFF`）**。
- **进度记忆**：每歌单记 `lastPlayedUri + lastPositionMs`（每 ~3s 落盘）。
- **分离产物**：缓存，**不属歌单**；多轨**不改**当前歌单。

### 实现要点
- **`PlaylistStore`**：加 `type/isDefault/lastPlayedUri/lastPositionMs`；`load()` 做**迁移**（无 type → 由 folderUri 推断；无默认歌单 → 自动建）
  + 新增 `recordProgress(listId, uri, pos)`。
- **`PlaylistViewModel`**：`createFileList/deleteList(禁默认)/clearList/moveTrack(仅 FILE)/addTrack(insertIndex)/recordProgress/filterExisting`。
- **`PlayerViewModel`**（核心）：**队列化** —— `playPlaylist(listId,startIndex)` 用 `setMediaItems(items,idx,0)`；
  `loadAndPlay(uri)` → **加入歌单 → 以歌单为队列播放**；`next/prev` = 原生 `seekToNext/PreviousMediaItem`；
  `applyRepeatMode()` 读设置；切歌清理（波形/进度/锚点）；
  **`onPlaylistRemoved(id)`**：清/删到当前歌单 → `stop()+clearMediaItems()+状态归零`；
  **`restoreFromSession()`**：Activity 重建/退桌面再进 → 从 Session 恢复 `hasMedia/曲名/歌单`。
- **接线**：`AppShell` 点歌单曲 → `playPlaylist(listId, idx)`；`PlayerScreen` 顶部显示“当前歌单 X/Y”；
  `PlaylistScreen` 当前曲高亮、类型、默认歌单禁删/清空、**文件歌单↑↓排序**；清/删 → `onPlaylistGone` → `playerVm.onPlaylistRemoved`。
- **设置**：`SettingsRepository.listEndBehavior`（LOOP 默认 / STOP）+ `SettingsScreen` 选项。

### ★ 波形：外环修复 + 缓存
1. **外环角度按真实全曲时长映射**（而非“已解码时长”）→ 否则流式增量时“前几秒波形铺满整圈”。
2. **取消旧提取**：`onChunk` 返回 `selfJob.isActive` → `job.cancel()` 能真正终止阻塞在 MediaCodec 的同步解码

   ⚠️ **只在 `complete` 时写**（`ExtractResult.complete`）——否则中途取消会缓存“半截波形”→ 命中后残缺。

### ★ 又一波修正（歌单交互细节，真机验证通过）

> 核心教训：“**队列 = 当前歌单**”这个不变量，**只在 `playPlaylist/startQueue` 时保证**；
> **任何“只改歌单不改队列”的操作都必须同步队列**（见下）。

1. **切歌标题不更新**：标题更新曾被包在 `if (playlistId != null)` 里 → **未选中歌单时切歌标题不变**。
   修：标题**无条件更新**（有 `metadata.title` 就更新）。
2. **重启后“哪个歌单都没选中”**：“当前选中歌单”只在内存。修：持久化到
   `SettingsRepository.activeListId`；VM init 时恢复（无效 → 默认歌单）→ **永远有选中歌单**。
3. **清空 ≠ 取消选中**：拆 `onPlaylistCleared`（清空：**保留选中**）/ `onPlaylistRemoved`（删除：回退默认）。
4. **删除当前歌单后“hasMedia=false”但不一致**：修：删除后回退默认歌单，**默认有曲则直接接着播**。
5. **选中文件夹歌单时不应能导入**：`PlayerState.playlistIsFolder` → `PlayerScreen` **隐藏“导入音频”**。
6. **歌单页数量不更新**：`PlaylistViewModel._lists` 是内存缓存，播放器改文件后它不知道。
   修：`reload()` + 进歌单页 `LaunchedEffect(currentListId) { reload() }`。
7. **排序/删曲后队列不同步**（队列≠歌单）：`removeTrack`/`moveTrack` 只改文件。修：
   - `onTrackRemoved`：删**非当前曲** → `p.removeMediaItem(qi)`（**不打断**）；删当前曲 → 重建接下一首；
   - `onTrackMoved`：`p.moveMediaItem(from,to)`（**不打断**）。
8. **高亮按“曲目身份（uri）”而非 index**：`PlayerState.currentUri`；`PlaylistScreen` 高亮用
   `t.uri == currentUri` → **排序/删其它曲后绿条不飘**（index 仅作“第几首/共几首”）。
9. **点同一个（当前）歌单不重播**：`selectPlaylist` 若 `listId==currentPlaylistId && hasMedia` →
   只 `play()`（不重建队列）。

> **操作序列静态推演（S1–S11）**：构造了冷启/导入/切歌单/清空/删除/排序/多轨回原曲等序列逐条对照代码，
> 发现同一类根因（队列未同步）并全部修复。**✅ 真机验证通过。**

### ★ R2 迭代：`Modifier.rotate` 的陷阱（竖滑块必须自绘）

**背景（用户报告）**：“音调先调低，等一小会再调高 → 报错 `ERROR_CODE_TIMEOUT`；

**✅ 真实根因（media3 1.11.1 源码 + 真机日志确证）**：

```
  at ExoPlayerImpl$ComponentListener.onStuckPlayerDetected
```

  ⇒ 频繁改参 → 频繁重建 Sonic → 吐不出 PCM → 位置不推进 → StuckDetector。
- ⚠️ **未确证**：为何停止改参后仍卡 30s 不恢复（单次重建预填充仅 ~30ms）。

**修法**（`PlayerViewModel.kt`）：
1. **防抖**：`applyPlaybackParameters` 只保留「最后一次」请求，静默 `PARAM_DEBOUNCE_MS=150ms`
   后再下发；下发前校验与 player 当前值是否相同。
2. ~~AudioSink 超时自动恢复~~ → 保留为 `recoverFromAudioSinkTimeout()`，
   但**实测对 StuckPlaying 类错误无效**（重建 sink 没救回来）。

- `--ez pitch_bugc_stress true`（**20s 内 6 次变速变调**，复刻失败时间线）：

| 路径 | 结果 |
|---|---|

### 调研：Sonic 替代方案（一手来源，**已完成 ①–④**）

> 纪律：`web_search` 仅作“可能性搜寻”，**结论一律以 README/官方文档/源码为准**。
> 完整报告：`research_timescale.artifact.md`。

**已读一手来源（结论）：**
1. **media3 `SonicAudioProcessor` / `Sonic` 源码**：
   - `setSpeed/setPitch` → 置 `pendingSonicRecreation=true`；真正的 `new Sonic()` 在 `flush()`。
   - `Sonic.flush()`：`inputFrameCount=0`（丢弃未产出输入）。
   - `Sonic.changeSpeed()`：`if (inputFrameCount < maxRequiredFrameCount) return;`（**块处理**）。
2. **SoundTouch（surina.net + codeberg）**：
   - 能力：独立 tempo/pitch/rate（对应 F2.1/F2.2）；**License：LGPL v2.1**；
     实时延迟 ~82ms（`sequenceMS` 默认）+ overhead，官方称 ~100ms；支持 Android。
   - 流式 API（`SoundTouch.h` 逐字）：`putSamples` / `receiveSamples` / `flush` +
     `setTempo/setPitch/setRate/setPitchSemiTones`。
   - 默认值（`TDStretch.cpp` 注释）：`sequenceMS=82ms / seekwindowMS=28ms / overlapMS=12ms`；
     AA filter 8–128 taps。
3. **★ 关键实验①（源码逐字确证）**：`SoundTouch::setTempo/setPitch/setRate` **不 new/delete**
   对象；`TDStretch::setTempo` **不调 `clear()`/`memset`**、不重置缓冲；
   `clear()` 只在构造调一次。
   ⇒ **改参保留缓冲/状态**（与 Sonic 的「改参→flush→new Sonic→丢缓冲」**相反**）
   ⇒ **原理上不会出现 Sonic 那种“频繁改参→饥饿→卡死”**。
4. **③ media3 `BaseAudioProcessor` 契约**：需实现 `onConfigure/onQueueEndOfStream/onFlush/onReset`
   + `AudioProcessor` 接口；工作量**中等**。
   - ⚠️ **关键陷阱**：media3 每次改参会调 `flush()`；若封装在 `onFlush()` 里重建 SoundTouch 实例
     就重蹈 Sonic 覆辙 ⇒ **必须只 flush 不重建**。
5. **④ 参考实现 `neboyang/VoiceChanger`**：CMake 从源码编 SoundTouch 2.4.1 + JNI
   （`soundtouch-jni.cpp` + `SoundTouch.kt`），走**独立 AudioTrack（无 ExoPlayer）**。
   ⇒ 不能直接用（我们要接 ExoPlayer 链），但可参考其 CMake/JNI 组织。

**结论**：SoundTouch 方向**可行且为当前最优候选**：不会卡死、低速声质应等同 Sonic（均 WSOLA）；
代价：LGPL 合规 + 自写 JNI/AudioProcessor + ~82ms 延迟。
**建议**：先做**最小验证**（不入主链），真机跑「高频改参不卡 + 低速声质」再决定接入。

**★ 补充调研（①②③ 补查，一手源码）：**
- **注入点（决定原型写法）**：`DefaultAudioSink.DefaultAudioProcessorChain` 构造器把
  `SonicAudioProcessor` **永远放在链尾** ⇒ `setAudioProcessors(...)` **无法移除 Sonic**（会叠加）。
  想真替换必须 **`Builder.setAudioProcessorChain(自定义链)`**；
  `AudioProcessorChain.applyPlaybackParameters()` 就是 media3 改参的入口
  → 在这里调 `SoundTouch.setTempo/setPitch`。
- **AA filter 陷阱**：`RateTransposer::setRate()` 只重算不 clear（✅）；
  **但 `enableAAFilter()` 默认会 `clear()`（清缓冲）** ⇒ **运行期不能反复切 AA filter**，只初始化设一次。
- **Rubber Band**：**GPL**（开源）/ 商业授权 → 授权上**劣于 SoundTouch（LGPL）**；官方页未明说 Android/ARM。作 Plan B。

- **不回弹**：`EqPanel` 用 `localDirty` 标记；拖动过的段**不再被快照回写覆盖**（含松手后）。
- **防爆音（关键）**：拖动中**只改本地视觉值、不下发**；**松手（`onValueChangeFinished`）才下发一次**精确值。
  原因：`audiofx.Equalizer` 每次 `setBandLevel` 都会让 HAL 重配效果链 → 每帧下发 = 爆音/咔嗒。
  **真机验证**：一次拖动只产生 **1 条** `setEqBand`（修复前为每帧 N 条）。

> ★★ **重要更正**：初期“EQ 调完听不出变化”被误判为“HAL passthrough / 需自实现 DSP”。
> 但 `dumpsys media.audio_flinger` 取证：效果链挂在**正确 session**、`Enabled=y`、值回读一致；
> 后改用 **±6dB** 极端曲线 → **听觉上一下就出来了**。真实原因是 **+3dB 幅度太小**（接近可辨临界）。
> **结论：平台 `android.media.audiofx.Equalizer` 在本机确实生效，不做自实现 DSP。**

#### ★ 3.1 后续修的两个回归 bug（用户真机反馈，已修复+验证）

**Bug A：一进分离页就“跳回播放器并重播”**

### 3.2 EQ 定案（✅ 平台 EQ 生效；不需软件 EQ）

**问题历程**：用户多次反馈“EQ 调了听不出变化”，我曾反复在两个结论间摇摆。**最终用受控实验定案**：

**受控 A/B 实验（新增 `CMD_APPLY_EQ_EXTREME`）**：一键把 5 段置全−15dB / 全+15dB。
- 真机 logcat：`EQ_EXTREME toMax=false mB=-1500 set=[-1500×5] readBack=[-1500×5]`（写入到 HAL 且回读一致）。
- **用户人耳确认：“有明显变化”** ⇒ **平台 `audiofx.Equalizer` 在本机确实生效**。
- ⇒ **方案 X（软件 EQ / biquad）作废**（之前基于“听不出”的 passthrough 结论已推翻）。

**为何之前“有时行有时不行”（根因，已修）**：
1. **下发行爲反复变更**（同一代码线里试了三种）：
   - 每帧下发 → 有声但**爆音**；
   - “松手才下发” → **拖动中完全静默**（用户感受为“拖了没反应”）← 主要嫌疑；
   - **限频下发（最终）** → 拖动中~10Hz 能听到 + 大幅减爆音。
2. **EQ 默认关 + 滑块曾置灰** → 有时根本没开启 EQ，拖了自然无反应。
3. **边缘 bug**：`EqController.setBandLevel` 在 `targetLevels` 为空时**丢弃首次写入**（已修：为空则按段数初始化）。

**最终实现（`EqPanel`）**：
- 滑块**始终可拖**（不置灰）；**拖动即自动开启 EQ**；
- **限频下发 `EQ_SEND_THROTTLE_MS=100ms`** + **松手补发精确终值**（一次拖动 ≈ 10 条 `setEqBand`，真机已验证）；
- **不回弹**（`localDirty` 标记，含松手后）；
- 默认微笑曲线（低/高 +3dB）。

**验证证据**：logcat `setBandLevels set=[...] readBack=[...]` 一致（写到 HAL）；用户人耳确认全 ±15dB 有明显变化。

**遗留/待观察**：EQ 挂在播放器 `audioSessionId`；若播放器中途重建 AudioTrack（换输出设备等）导致会话变更，
需在下一个 `STATE_READY` 重挂（目前实现如此）。单轨/多轨均已验证会话匹配（`dumpsys` effect session == 播放轨 session）。
