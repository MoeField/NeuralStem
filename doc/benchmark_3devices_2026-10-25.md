# 三设备 benchmark 实测（2026-10-25）

> **目的**：验证「模型体积 → 分离速度」的映射是否跨设备稳定，
> 为「模型库按速度/体积分组」提供数据依据。
>
> **口径**：纯推理 RTF（`DeviceBenchmark`，合成音频，预热后计时，LONG 模式 3 轮取中位）。
> **不含解码/IO** —— 测的是模型算力，不是文件读取。
> **RTF** = 实时倍率。`9×` = 1 秒处理 9 秒音频。**>1× 才可能边分离边播。**

## 三、核心结论

### 3.1 体积 → 速度簇：三设备完全一致 ⭐

| 体积 | BF00A | OPPO | Gen3 | 簇内一致性 |
|---|---|---|---|---|
| **28MB** | 1.02–1.03× | 0.94–1.00× | 1.87–2.24× | ✅ 全部最快 |
| **50MB** | 0.52×（历史） | 0.48× | 0.98–1.00× | ✅ 第二 |
| **56MB** | 0.41×（历史） | 0.38× | 0.75–0.77× | ✅ 第三 |
| **64MB** | 0.35× | 0.31–0.34× | 0.69–0.73× | ✅ 最慢 |

**三台设备、三个 SoC、三个价位，簇的边界与顺序完全相同。**
⇒ **体积是速度的可靠代理**（物理原因：体积 ≈ `dim_f` 频谱宽度，直接决定矩阵乘的计算量）。

### 3.2 绝对倍率差很多，但比例稳定

| 指标 | BF00A | OPPO | Gen3 |
|---|---|---|---|
| Spleeter 2-stem | 8.59× | 9.47× | 21.26× |
| 28MB UVR 均值 | ~1.01× | ~0.97× | ~2.01× |
| 64MB UVR 均值 | ~0.35× | ~0.32× | ~0.71× |
| **Spleeter ÷ 64MB** | **24.5** | **29.6** | **29.9** |

⇒ **跨设备不能硬编码 RTF**，但**簇的相对关系可以硬编码**。

### 3.3 对分组设计的直接结论

| 事项 | 结论 |
|---|---|
| **分组键** | ✅ 保持**体积**（跨设备稳定、有物理意义） |
| **节头 RTF** | ❌ 不能硬编码 `≈0.34–0.35×`（那是 BF00A 的数字，Gen3 上实际 0.72×）<br>✅ 应从 `DeviceBenchmark.cached()` 读**本机实测值** |
| **未装模型** | 按体积簇归属，节头注明“未装模型按体积估算” |
| **正式 vs 实验** | 体积撞车（64MB 有 8 个）→ 用**行内标签**区分，不做二级分组键 |

## 四、★ 事故记录：热降频污染（重要经验）

### 现象

2026-10-24 在 BF00A 连跑 18 个模型（LONG，约 16 分钟），**第 8 个之后 RTF 全部掉 30–38%**：

```
uvr-Voc_FT    0.348× → 0.348×   （前段，正常）
uvr-Inst_1    0.338× → 0.348×   （前段，正常）
uvr-Inst_2    0.338× → 0.312×   ← 开始掉
uvr-Inst_3    0.337× → 0.233×   ← −31%
uvr-Inst_HQ_1 0.346× → 0.213×   ← −38%
uvr-9703      1.010× → 0.672×   ← −33%
```

### 根因（实查）

```
Thermal Status: 2  (MODERATE)
CPU 温度: 53.9°C
cpu0 scaling_cur_freq = 500 MHz  /  cpuinfo_max_freq = 2000 MHz  → 25%
cpu4 scaling_cur_freq = 500 MHz  /  cpuinfo_max_freq = 2000 MHz  → 25%
cpu7 scaling_cur_freq = 2200 MHz /  cpuinfo_max_freq = 2200 MHz  → 100%
```

中端机散热不足，连续高负载后小/中核被压到 25%。

### 修法（`ThermalProbe` + 分批冷却）

1. **每次测量采集热状态**（`ThermalProbe.Snapshot`）：热状态 / 温度 / 大核频率比
2. **数据带可信度标记**：日志输出 `⚠️SUSPECT`，写进缓存 JSON
3. **分批跑**：每 4 个模型等设备冷却（`batchSize=4`）
4. `BENCH_QUALITY` 汇总行报告有多少条可疑

## 五、★ 判据演进：为什么不能用「最小频率比」

### 初版（错误）

```kotlin
freqRatio = allCores.map { cur / max }.min()   // 最小
suspect = freqRatio < 0.80f
```

**在 OPPO 上首次运行就误报**：

```
thermal=NONE freq=25% ⚠️SUSPECT     ← 误报！
实际：cpu0-7 = 32%~47%（空闲调度，没负载）
```

### 两个错误

| # | 错误 | 说明 |
|---|---|---|
| 1 | **取 min** | 小核本来就低频，min 几乎永远 < 80% |
| 2 | **测量前采样** | 推理还没开始跑，采到的是空闲频率 |

### 现版（正确）

```kotlin
// 1. 在【每轮推理跑完之后】采样（此时 CPU 处于负载态）
// 2. 只看【大核】频率比（ORT 线程池优先大核）
val idle = bigCoreRatio < 0.40f          // 空闲：大核也低
val suspect = !idle && (               // 有负载 且
    thermalStatus >= 2 ||               //   热状态告警
    bigCoreRatio < 0.80f                //   或大核被压
)
```

三种形态的正确判定：

| 形态 | 大核 | 小核 | 判定 |
|---|---|---|---|
| 空闲 | 32% | 25% | **不可疑**（数据无效但非污染）|
| 正常负载 | 95% | 40% | **不可疑**（小核低是常态）|
| 热降频 | 50% | 25% | **可疑** |

已用 `ThermalProbeTest`（14 项）钉死。

## 六、复现命令

```bash
ADB=/Volumes/SA500/Library/Android/sdk/platform-tools/adb
S=<serial>
PKG=pub.miku.neuralstem

# 1. 装模型（约 7 分钟，1.2 GB）
$ADB -s $S shell am start-service -n $PKG/.devtools.TestCommandService \
  --es cmd dlmodel --es a0 all

# 2. 跑 benchmark（分批 + 冷却，防热降频）
$ADB -s $S shell am start -n $PKG/.spike.SpikeActivity \
  --ez benchmark true --es bench_mode long --ez bench_all true --ei bench_batch 4

# 3. 看结果
$ADB -s $S logcat -d -s DevBench:I | grep -E "bench |BENCH_DONE|BENCH_QUALITY"
```

**夜间测试规范**（必守）：测前把系统媒体音量调到 1，EQ 全拉到 −10 dB。
