## Task 0b — Spike 工程构建

**步骤：**
1. 依赖接入：AAR 放 `app/libs/sherpa-onnx-1.13.8.aar`
2. `spike/` 包：WavIo（RIFF 解析）→ Chunker/SpleeterSeparator（TFLite 遗留）
   → SherpaSourceSeparation + SpikeViewModel + SpikeActivity
3. JNI 胶水：`sherpa_spike.c` + `CMakeLists.txt`，链接 AAR 解包出的 `libsherpa-onnx-c-api.so`
4. `:app:assembleDebug` 通过；APK 内含全部所需 `.so`

### 坑 1. [环境·已解决] Mac 代理导致 Gradle 无法下载 / 证书错误
- **症状 A**：`No route to host`（dl.google.com 直连不通）
- **根因**：系统 HTTP 代理 127.0.0.1:26561（Steam++）做 TLS 解密（MITM），
  Gradle JVM 不认它的证书链 → PKIX 校验失败；不配代理则直连被墙
- **错误尝试**：改用 SOCKS5 127.0.0.1:1080（sslocal）可以构建成功，但**触发 IDE 代理认证弹窗**
  （`systemProp.socksProxy*` 被所有 JVM 读取，IDE 内置网络层连过去时 sslocal 要求用户名/密码）
- **当时的方案**：`settings.gradle.kts` 里 google() 仓库 URL 用「自建 URL 前缀代理」
  ⚠️ **该方案已在 Task 1 废弃**，见下方坑 9

### 坑 2. [构建] NDK / CMake 版本必须显式指定
- **症状**：`NDK not configured. Preferred NDK version is '28.2.13676358'` → 装的是 30.0.16248370
- **症状**：`CMake '3.22.1' was not found in SDK` → SDK 里装的是 4.1.2
- **解法**：`ndkVersion = "30.0.16248370"`、`cmake { version = "4.1.2" }`，都用本机已装的版本
- ⚠️ **换机器要重新确认这两个版本号**

### 坑 3. [构建] sherpa-onnx 不在 Maven Central
- `com.k2fsa.sherpa.onnx:sherpa-onnx-android` → 404
- **官方用法**：下载 release 里的 AAR 直接放 `app/libs/`，用 `fileTree` 引入
- 同时需 `packaging.jniLibs.pickFirsts += "**/libsherpa-onnx-c-api.so"`
  （AAR 与 `cpp/sherpa-libs` 各有一份）

### 坑 4. [JNI] 库加载顺序
- `libsherpa-onnx-jni.so`（AAR 自带）的符号表里**没有** SourceSeparation 相关函数
- 必须按 `onnxruntime → sherpa-onnx-c-api → neuralstem_spike` 顺序 `System.loadLibrary`，
  否则 unsatisfied link

### 坑 5. [JNI] 构造器签名多写了一个 `L`（★最隐蔽的坑）
- **症状**：`NoSuchMethodError: no non-static method "...SeparationResult.<init>([FL[FI)V"`
- **根因**：C 侧 `GetMethodID` 签名写成 `"([FL[FI)V"` —— 第二个 `[F` 前多了一个 `L`
- **正确**：`"([F[FI)V"`（`float[] vocals, float[] accompaniment, int sampleRate`）
- **教训**：JNI 签名无编译期检查，只能运行时炸。**必须靠自动化日志定位** ——
  正因如此，Task 0c 的自动化通道是必需品而非锦上添花

### 坑 6. [数据] 动态 shape 的模型输出长度 ≠ 输入长度
- sherpa 输出 1150976 帧 vs 输入 1151115 帧，**少 139 帧（≈3ms）**，STFT 边界效应
- **教训**：不能假设输出与输入等长；TFLite 版代码里也必须在 `allocateTensors()` 后
  从 `getOutputTensor().shape()` 查实际尺寸
- 后续在 Task 0e 精确推导出规则，见坑 12

### 坑 7. [API] SAF 流不可 seek
- `contentResolver.openInputStream(uri)` 是流式，WAV 解析需要 `RandomAccessFile` 随机访问
- **解法**：先拷到 `cacheDir` 再解析

### 坑 8. [已知风险→已闭环] so 未做 16KB 对齐
- **当初**：`libsherpa-onnx-c-api.so` 非 16KB 对齐 → Android 15+ 设备受限。
  Spike 用 `useLegacyPackaging = true` 放行
- **Task 0g 实查**：扫描 APK 内全部 so 的 ELF `PT_LOAD` 段 ——
  sherpa 全家 + 本项目胶水**均 16KB 对齐** ✅，唯 3 个 **TFLite so 仅 4KB 对齐**
  （`tensorflowlite_jni` / `tensorflowlite_flex_jni`）
- **处置（用户决策）**：TFLite 回退路线废弃，代码存档不删除
  - `SpleeterSeparator.kt` / `Chunker.kt` → `app/src/deprecated/java/`（非源集，不编译不打包）
  - 删 `build.gradle.kts` 两个 TFLite 依赖；`libs.versions.toml` 的 alias 加废弃注释保留
  - `app/src/deprecated/README.md` 记录完整选型演进链与恢复方法
- **验证**：构建 ✅ 17 单测 ✅ APK 内 12 个 so 全部 16KB 对齐 ✅ 端到端回归 23.38× ✅
  → 双向对齐警告清零
- **教训**：第三方 so 的对齐问题在接入时就该扫 ELF 头（3 行 python），
  而不是等 Android 15+ 真机上炸了再查

## Task 0c — 自动化测试通道（★ 重要教训）

### 问题：Agent 用 `adb shell input tap` 多轮点击「点不动」

**当时的方法栈：** `adb shell input tap <坐标>`（坐标取自 accessibility bounds）
+ `ui_state`/`take_screenshot` 回读 + `logcat` 佐证。

**观察到的矛盾：**

| 观察 | 含义 |
|------|------|
| `input tap` 退出码 0，logcat 有 `Input` 启动记录，**无 SecurityException** | 事件已注入，非权限问题 |
| 坐标在按钮 bounds 内，节点也已无 `enabled="false"` | 坐标确实落在可用+clickable 的按钮上 |
| 点击后 UI 仍是原态，**零条我方日志**；但 `startSeparation()` 的两条 early-return 都会置 Error 态 | ⇒ 函数**根本没被调用**，点击没到达 Compose |
| 用户**手动点击**生效 | 真人点击可达，应用与 dump 都活着 |
| `keyevent HOME` 后 `mCurrentFocus` **逐字节相同**，前后截图**像素一致** | ⇒ **IDE 设备视图返回过期帧** |

**两个候选根因（未做决定性实验区分）：**
- (a) API 25 模拟器上注入的 motion event 未送达 Compose 按钮
- (b) IDE 设备视图镜像返回陈旧帧，污染了「没反应」的判断

**教训：坐标注入 + IDE 设备视图回读，是不合格的自动化底座** —— 黑盒、时序脆弱、不可交叉验证。

### 解决方案（三层）

- **Phase A ✅ 应用内自驱动**：ViewModel 把加载/分离拆成 `suspend` 内部版 + `launch` 公开版，
  `runAutoSpike()` 在同一协程内串联；
  `adb shell am start -n pub.miku.neuralstem/.spike.SpikeActivity --ez auto true` 触发
- **Phase B ⬜ 仪器化测试**（`onNodeWithText(...).performClick()` 语义查找，不用坐标）—— 待做
- **Phase C ✅ 验收铁律**：证据一律走非 UI 通道
  （logcat / `run-as ls` + `adb pull` + WAV 头校验 / `dumpsys`）

**附带踩坑：** `SpikeActivity` 里写的 `vm.state.observe(this)` 是**编译错误**
（`StateFlow` 无 `observe`），已改为 ViewModel 内部串联。

## Task 0e — 长音频流式改造

**步骤：**
1. E1 `WavIo` 三层化：probe / WavReader / WavWriter（头部回填，close 时 seek 4/40 写真实 size）
2. E2 新增 `StreamingSeparator`（分块 + 交叉淡化 + 顺序落盘）+ 17 项单测
3. E3 `SpikeViewModel` 切流式：probe 只读头，分块流式推理，块级进度真接线
4. E5 全曲实测：5:14 → 22 块 → 22.4s（14×），峰值 PSS 680MB 且稳定，无 OOM

**结论：整曲驻留内存的架构在 48MB 堆上不成立，分块是唯一出路；分块后内存与总长无关。**

### 坑 9. [内存·已解决] 整曲入堆必 OOM，分块后峰值稳定
- **症状**：`OutOfMemoryError: Failed to allocate a 55397576 byte allocation`（5:14 全曲，
  27.7M float ≈ 110MB vs 48MB 堆）崩在 `WavIo.read()`
- **根因**：API 25 模拟器 `dalvik.vm.heapgrowthlimit=48m`；而 Kotlin 侧整曲 FloatArray +
  native 侧 Eigen 缓冲（`2×num_frames×1024` float）都随时长线性增长
- **解法**：三层流式 + App 层分块（sherpa **不做**内部分块，读上游源码已证）
- **验证**：全曲 22 块实测，峰值 PSS 从首块后即稳定在 680MB，不再随进度增长

### 坑 10. [构建] 单测里 `android.util.Log` 会炸
- **症状**：`Method i in android.util.Log not mocked`
- **解法**：`testOptions.unitTests.isReturnDefaultValues=true`（Log 变空操作），
  纯逻辑类（StreamingSeparator）得以直接 JVM 单测，注入假分离器逐样本断言

### 坑 11. [算法·已验证] sherpa 单次调用的输出长度规则
- **实测推导**：`N_out = N_in − (N_in mod 1024)`，输出恒为 1024 的整数倍
  （用 0d 的 1151115→1150976 拟合，完全吻合）
- **影响**：每次调用尾丢最多 1 hop（1023 帧 ≈ 23.2ms）⇒ 交叉淡化窗口只需 >1 hop
  （取 4096，4× 余量）；尾部丢失帧由下一块覆盖，前提是 `overlap > 1024`（约束 A）

### 坑 12. [算法·正确性前提] `chunk ≥ 2×overlap`（违反时静默产出坏音频）
- **推导**：块分 head/body/tail 三区，只有 `overlap ≤ hop` 时 body 才「只被本块覆盖」
  → 才能直写原始样本（零拷贝）；否则一帧被 3 块覆盖，归一化失效
- **处置**：`requireChunkGeometry` 直接拒绝，而不是产出错误音频；
  仅在真分块（>1 块）时校验 —— 单块无重叠区，曾因无条件校验误拒合法短音频（测试抓出）

### 坑 13. [方法论·★重要] 判断拼接边界好坏的判据选择
- **错误判据 1**「边界最大样本跳变 vs 全局 p99.99」：误报 12/21（电波曲瞬态大）
- **错误判据 2**「边界 vs 随机窗口最大跳变」：仍误报 16/21（同样被瞬态淹没）
- **正确判据**「能量守恒残差：淡化区残差 vs 紧邻非重叠区残差」：1.19×，无系统性不连续
- **教训**：音乐瞬态会淹没一切样本级跳变统计；**必须用与拼接相关的守恒量**
  （Spleeter 软掩码 ⇒ vocals+accomp≈src）做对比。第一反应的判据不可靠。

## Task 0f/0g — 多引擎实验与环境重测

### 坑 14. [JNI·C-API] 同一入口支持多引擎类型（Spleeter/UVR）
- C 侧 `nativeCreate` 加 `jint mode` 参数：0=Spleeter（双模型）1=UVR（单模型），
  由一个入口按 mode 填充不同的 config 子结构，避免 JNI 导出膨胀
- Kotlin 侧 `accompPath` 改为可空（`String?`），`ReleaseStringUTFChars` 判空后再释放
- 输出目录按引擎名隔离（`stems-spleeter` / `stems-uvr-*`），A/B 对比不互覆

### 坑 15. [内存·环境限制] UVR-MDX 在 1GB 模拟器上不可行（非代码 bug）
- **现象**：官方 UVR 模型（66.8MB fp32 / 29.7MB）首块或次块推理中进程被静默 SIGKILL，
  **无 tombstone、无 bad_alloc** —— kernel LMK 干的
- **决定性数据**：小模型首块跑完时 PSS 已 612MB（整机 1GB/可用 754MB），第二块即死；
  Spleeter 同机全曲 680MB 却能活 —— UVR 单块 arena 需求更高
- **教训**：
  a) 「官方 CI 能跑」≠「低内存设备能跑」，新模型必须先小步验证内存
  b) **无 tombstone 的静默死 = kernel SIGKILL**，别往 native crash 方向查
  c) 真机（≥3GB）重试的管线已全部就绪（mode 参数/模型热切换/目录隔离）

### 坑 16. [算法·★修正] UVR 与 Spleeter 的块长-内存规律**完全相反**
- 6G 环境重测推翻 0f 时的推断（当时块还没跑完就死了，根本没观察到块长差异）

| | Spleeter | UVR-MDX |
|---|---|---|
| forward 激活 | 与块长**无关** | **随块长线性涨**（切段 batch 一次 forward） |
| 安全块长 | 15–30s | **必须 ≤5.92s**（模型内部 chunk = `(dim_t-1)×hop`） |
| 15s 块实测 | 稳定 | **RSS 5.8GB → 被 LMK 杀**（6G RAM 也扛不住） |

- **教训**：**负结果实验的结论边界要格外小心** —— 设备能力不足时的「都失败」
  可能掩盖真实规律
- **回归**：Spleeter 主线未受影响（喀秋莎 19.98× 实时）

### 坑 17. [质量评价·方法论] 「模型对不对」的验证必须与「好不好听」分开
- 喀秋莎 `vocals≈0` 的乌龙：先误判「厚合唱导致模型失效」，再被用户澄清那是**纯音乐** ——
  `vocals≈0` 是模型对 instrumental 的**正确输出**。带人声版复跑 vocalsRMS=0.089 ✅
- **教训链**：①先验证输入假设（素材对不对）→ ②自动质量指标（RMS/corr/守恒）
  → ③人耳试听。**顺序不能反**
- **副产品**：vocals RMS 可反向用作「纯音乐自动判据」

## Task 0 阶段总结

**用户对 2-stem 质量的主观评价：「能对付，但是谈不上完美。」**

  （UVR-MDX/htdemucs/sherpa 官方多轨）已预留，Task 4 后评估

### 坑 56. [★重要·R2] 频繁变速变调 → `ERROR_CODE_TIMEOUT`：**不是** AudioSink 超时，是 `StuckPlayerDetector`

> 注：本条早期误编为“坑 48”（与已有的 JNI 坑 48 撞号），已更正为 **坑 56**。

**现象（用户报告）**：音调/速度短时间多调几次 → `ERROR_CODE_TIMEOUT`；
播放键点了进度不动、拖进度条也不能恢复。

**★ 错误的第一结论（必须纠正）**：初期凭经验/二手搜索判定为
“`DefaultAudioSink` 重配 AudioTrack 超时”。**实测推翻**。

**真实根因（media3 1.11.1 源码 + 真机日志确证）**：
```
Caused by: androidx.media3.common.util.StuckPlayerException:
  Player stuck playing with no progress for 10000 ms
  at ExoPlayerImpl$ComponentListener.onStuckPlayerDetected
  at StuckPlayerDetector$StuckPlayingDetector.update
```
- media3 内建 `StuckPlayerDetector`（**1.11.1 默认开启**）：`player.isPlaying()==true`
  但 `getCurrentPosition()` 连续无推进→ 报错。
- 源码：`ExoPlayer.DEFAULT_STUCK_PLAYING_DETECTION_TIMEOUT_MS =
  isRunningOnEmulator() ? 30_000 : **10_000**` —— 日志的 10000ms 即此。
- 可配：`ExoPlayer.Builder.setStuckPlayingDetectionTimeoutMs(ms)`；
  全局开关 `ExoPlayer.experimentalEnableStuckPlayingDetection`（实验性）。

**为何位置不推进（Sonic 源码确证）**：
- `SonicAudioProcessor.flush()` 中 `pendingSonicRecreation` → **`new Sonic()`**；
  `Sonic.flush()` 把 `inputFrameCount = 0`（**丢弃已攒但未产出的输入**）。
- `Sonic.changeSpeed()` 开头：`if (inputFrameCount < maxRequiredFrameCount) return;`
  —— **块处理**，攒不满 `2*(sampleRate/65)` 帧就不吐数据。
- ⇒ 频繁改参 → 频繁重建 → Sonic 不断被清零 → 长时间吐不出 PCM
  → `getCurrentPosition` 不推进 → 触发 StuckDetector。
- ⚠️ 仍**未确证**：为何停止改参后**仍持续卡 30s 不恢复**（单次重建
  预填充仅 ~30ms）。需运行时抓 `audio_flinger` 或给 Sonic 加内部日志才能定论
  —— **不得凭猜测写结论**。

**实测证据（真机 BF00A，`gn.mp3`，同一压力序列：20s 内 6 次变速变调）**：

| 路径 | 结果 |
|---|---|
| Sonic + 默认 10s | ❌ `ERROR_CODE_TIMEOUT`（卡死） |
| Sonic + 30s（方案1）| ❌ **仍卡死**（30s 时位置仍不动 ⇒ 非“短暂饥饿”）`resume@17784ms` |
| **AudioTrack 原生路径（方案3）** | ✅ **通过**：`pos=29652` 真实前进、无错误 |

**方案 3 做法（已实测可行）**：自建 `DefaultRenderersFactory
.setEnableAudioOutputPlaybackParameters(true)`（旧名 `setEnableAudioTrackPlaybackParams`），
经 `ExoPlayer.Builder(context, renderersFactory)` 注入；
`DefaultAudioSink` 会**绕过 Sonic**（`useAudioOutputPlaybackParams()==true`
⇒ `audioProcessorPlaybackParameters=DEFAULT`），由原生 `AudioTrack.setPlaybackParams()`
接管 speed **与** pitch。
- **取舍**：原生 speed/pitch 是**重采样级**实现 → **低速(<1x)音质明显降级**
  （用户实测：“只有速度向下调整音质下降会很明显”——物理必然，采样点变稀疏）。
  对“扒谱/跟练”核心场景（低速）不利。
- 单轨与多轨**必须用同一套** RenderersFactory，否则两路径行为不一致。

**教训**：
1. **错误码不可字面解读**：`ERROR_CODE_TIMEOUT` 在这里是 StuckDetector 发的，
   与 AudioSink 无关。**必须看异常栈/Cause 再下结论**。
2. **二手搜索不能当结论**（违反协作约定 2）：本次先凭二手判定 AudioSink 超时，
   再去读 media3 源码才发现是 StuckPlayerDetector。**一手源码为准。**

**待办**：调研是否可用成熟库（SoundTouch 等）替代 Sonic 做“低速好音质 + 不高频重建卡死”
（见 [`.memory.md`](.memory.md) 的调研小节）。

### 坑 29. [真机] `MediaFormat.KEY_PCM_ENCODING` 可能不存在 → NPE
- **症状**：`NullPointerException: Attempt to invoke virtual method 'int java.lang.Integer.intValue()' on a null object reference`
  （真机分离 MP3 时抛；模拟器同代码正常）
- **根因**：`KEY_PCM_ENCODING` 是 **API 24+ 的可选字段**，
  部分解码器不提供 → `getInteger()` 内部返回 null → 自动拆箱抛 NPE
- **解法**：`if (format.containsKey(KEY_PCM_ENCODING)) getInteger(...) else ENCODING_PCM_16BIT`
- **教训**：**MediaFormat 的可选键一律先 `containsKey` 再取**，
  尤其是 `KEY_PCM_ENCODING` / `KEY_DURATION`（后者还要注意是 Long 不是 Int）。
  这类问题只在特定设备/解码器上暴露，模拟器测不出来

### 坑 31. [架构·★重要] 两条入口复制同一段逻辑 → 漏改一半

- **解法**：抽出 `subscribeRepo(onFinal)`，两条路径共用
- **教训**：**同一段逻辑存在两个入口时，必须抽公共函数**。

  而且因为自动化路径能跑通，测试掩盖了按钮路径的缺陷

### 坑 32. [测试方法] `am start` 直启的 Activity 无父级,setResult 丢失
- **症状**：`am start SpikeActivity` 后点「去多轨播放」，直接回 launcher，无任何日志
- **根因**：`am start` 启动的 Activity **没有父 Activity**；

  （`registerForActivityResult` 是在 MainActivity 上注册的）
- **正确做法**：自动化要走**完整导航路径**
  （`am start MainActivity` → 点「Spike 分离」→ 在库里操作）
- **教训**：**涉及 Activity 间结果的流程，不能直接 `am start` 目标页**；
  这与坑 20（`am start` ≠ 重建）同源 —— 都是「`am start` 与真实用户路径语义不同」

### 坑 33. [UI] 「按钮路径」与「异步状态」的时序
- 按钮点击 → `repo.start()` 是异步的，完成可能在几百 ms（缓存）或几十秒（真跑）
- 必须先 `subscribeRepo()` **再** `repo.start()`，否则快速终态（缓存命中）会错过
- 与竞态相关：`StateFlow` 会重放当前值，所以订阅后立即收到 `Preparing`

### 坑 34. [多轨·★重要] 监听器注册时机 —— 在 load() 前注册会扑空
- **症状**：多轨播放时 UI 时长恒为 `0:00`（`duration=0ms`），
  用户反馈「伴奏没声音」（时长 0 导致进度/波形全失效，听感上像没在正常播）
- **根因**：
  ```kotlin
  val controller = multiTrack ?: MultiTrackController(...)   // tracks 为空
  controller.addListener(...)      // ← 遍历空集合，监听没挂上
  controller.load(...)             // ← 这里才创建 tracks
  ```
  `addListener` 只给**当前已存在**的轨挂监听 → 在 `load()` 之前调用必然扑空；
  而 `load()` 会重建全部轨，监听也不会自动继承
- **解法**：controller 内部保存 `listeners` 列表，
  `load()` 时给每个新建的 player 逐一 `addListener`
- **教训**：**监听器/观察者的注册要区分「对象生命周期」与「集合内容生命周期」**。
  集合会被重建时，注册点必须在重建之后（或框架代管转发）

### 坑 35. [多轨] player.volume 有两个写入点 → 互相覆盖
- **症状**：调节某轨音量后，另一轨音量可能被意外重置
- **根因**：`Track.volume/muted` 的 setter 直接写 `player.volume`，
  而 `applySoloMute()` 也写 `player.volume` —— **后者知道 solo，前者不知道**，
  两个写入点交替调用会互相覆盖
- **解法**：`Track` 的 setter 只改字段；**唯一**写 `player.volume` 的出口是
  `applyEffectiveVolume()`，由 controller 的 `applySoloMute()` 统一计算
  （优先级：独奏 > 静音 > 设定音量）
- **教训**：**同一状态有多个写入点时，必须收敛到单一出口**。
  音量这种「多规则叠加」（volume/mute/solo）的状态尤其容易出这类 bug

### 坑 36. [多轨] 异步 prepare 期间读 duration 恒为 0
- **根因**：`ExoPlayer.prepare()` 是异步的，`load()` 返回后立即读 `duration`
  一定是 0；必须等 `onPlaybackStateChanged(STATE_READY)` 才有效
- **解法**：`loadMultiTrack` 里先读一次（可能为 0），
  在 `onPlaybackStateChanged` 回调里**补写** `durationMs`
- **教训**：**ExoPlayer 的 duration/位置等属性都要等 STATE_READY**；
  同步读取必须容忍 0 值，并靠监听器补正

### 坑 37. [多轨·★★最关键] 多个 ExoPlayer 实例抢音频焦点 → 只剩一条出声
- **症状**：多轨播放「一会人声没、一会伴奏没」，反复无常
- **取证**（`dumpsys audio` 看该应用进程的 AudioPlaybackConfiguration）：
  ```
  # 修复前：只有 1 个 started
  piid:2415  state:idle     channelMask=0x0   ← 单轨 player(已 pause)
  piid:2423  state:started  channelMask=0x3   ← 只有 1 条 stem 在播
  ```
- **根因**：`MultiTrackController.load()` 给**每个** ExoPlayer 都设了
  `handleAudioFocus = true`。Android 的音频焦点**同一时刻只允许一个持有者**，
  载入 N 条轨时会有 N 次 `requestAudioFocus`：
  - 后申请者拿到焦点
  - 先申请者收到 `AUDIOFOCUS_LOSS`
  - **ExoPlayer 收到 LOSS 会自己 pause()** → 最终只剩最后一条在出声
- **解法**：**多轨共享一次焦点会话** ——
  - 只有**主轨（第一条）** `handleAudioFocus = true`
  - 其余轨 `false`（不参与焦点）
  - 由 controller 给主轨挂焦点监听，主轨失焦时**暂停全部轨**（guide N3 语义）
- **验证**：修复后 `dumpsys audio` 显示 **2 个 `state:started`**（都带 `channelMask=0x3`）
- **教训**：**方案 A（多实例）最容易踩的就是「每个实例都当自己是独立播放器」**。
  音频焦点、媒体会话、通知等**进程级单例资源**必须由 controller 统一持有，
  否则 N 个实例会互相踩。
  > 这类问题的特征是「表现不稳定」（取决于申请时序），
  > 比「一直坏」更难查 —— 必须用 `dumpsys audio` 这类非 UI 通道取证。

## 阶段 V — 功能可行性验证

> 用户决策：本轮聚焦「功能可行性验证」，UI 设计（Phase 6 / F5.x）推迟 1–2 周后单独讨论。

### 坑 38. [方法论·★重要] 互相关延迟估计要求「共享可辨识信号」

**场景**：V1 验证多轨对齐时，用互相关峰值 lag 判「两轨是否有相位偏差」。

**症状**：扫描 57 个窗，大部分 lag=0，但个别窗报出 −191/−200（贴搜索边界），
把结论从 PASS 翻成 FAIL。

**两个错误判据（先后都踩了）**：
1. **尾部静音窗**：文件末尾 `tailLoss` 区两轨 RMS 均为 0.0000；
   静音互相关无意义 → 峰值贴边界，且 `max_lag` 设多大就报多大（−200/−2000/−10000）。
2. **低相干窗**：某窗 `RMS_v=590 而 RMS_a=14169`（人声近乎静音的纯器乐段），
   两轨**无共享信号**，互相关被噪声主宰 → 同样贴边界。

**根因**：互相关延迟估计的前提是**两轨共享一个可辨识的信号成分**。
在静音/低相干区做互相关，得到的必然是无意义值。

**解法**：判据必须先保证**可观测性**——只在「两轨都有实质能量」的窗上判 lag，
其余窗标记为「不可判」而非「失败」。

**教训**：**先保证可观测性，再谈数值**。负结果实验（尤其是「没有信号」的场景）
比正结果更容易得出错误结论 —— 与坑 17（UVR 块长规律误判）同源。

### 坑 39. [测试·★重要] 互相关 fixture 不能用反相/周期信号

**场景**：把坑 38 的方法固化为单测时，设计「假分离器」注入音频。

**症状**：用「反相信号」fixture（vocals=x, accomp=−x）时，互相关峰值
不在 lag=0，而在自相关最小处（随机位置）→ 报出伪 lag（实测 −55/−27）。

**根因**：
- 反相是**负相关**：`v·a[+lag] = −Σv[i]v[i+lag]`，最大化它等价于**最小化**自相关，
  而自相关最小值出现在哪里与真延迟无关 → 延迟**不可辨识**。
- 同理**周期信号**（锯齿/正弦）也不可：自相关多峰，互相关峰值不唯一。

**解法**：fixture 必须让两轨**共享同一信号成分**（正相关），例：
`vocals = x`、`accomp = 0.6·x`，峰值唯一落在真延迟处。
信号用**确定性伪随机**（LCG，自相关为尖锐单峰）。

**教训**：**测试的「基准真值」必须真的可识别**。
一个看似合理的合成信号，可能根本不具备反推目标量的信息量 ——
此时测出的「失败」是测试的错，不是被测代码的错。
（本次先证明了「阳性对照能检出注入偏移」，才敢相信「lag=0」是真结果。）

### 坑 40. [V2·N4] MediaController 异步连接 → 早期请求静默丢失

**场景**：把单轨 player 从 VM 移到 `PlaybackService`（MediaSessionService），
VM 改用 `MediaController` 连接 session。

**症状**：`auto_play` / SAF 导入后「没反应」，logcat 实录：
```
PlayerVm: loadAndPlay: test.mp3
PlayerVm: loadAndPlay ignored: controller not connected yet   ← 静默丢弃
PlaybackService: service created, session ready
PlayerVm: MediaController connected to PlaybackService       ← 118ms 后才连上
```

**根因**：`MediaController.Builder(...).buildAsync()` 返回 `ListenableFuture`，
连接是**异步**的（实测 ~120ms）。而 `loadAndPlay` 在 `onCreate` 里就立即调用，
此时 controller 还没就绪 → 请求被丢弃。

**解法**：新增 `pendingLoad: (Player) -> Unit`：
- 连接未就绪：存下请求（`pendingLoad = { p -> doLoad(...) }`）
- 连接完成回调里：取回并重放（一次性）

**教训**：**把同步 API 换成异步后，所有「立即调用」的入口都要处理未就绪窗口**。
这与坑 34（监听器在 `load()` 前注册会扑空）是同一族问题 ——
「对象还没准备好就被使用」。差异是坑 34 是**集合内容**未就绪，
本坑是**连接**未就绪。

## 阶段 M — 分离模型探索

### 坑 41. [★ 环境] Android 16 下 adb push 的文件 app 读不到

**场景**：阶段 M 环境重建时，向 app 外部目录 push 测试音频，
但 `SpikeActivity --ez auto true` 报「下没有音频文件」。
而 `adb shell ls` **确实能列到文件**。

**实测三种落点（均失败）**：

| 落点 | 现象 |
|---|---|
| `adb push` → 外部 `Android/data/<pkg>/files/spike/` | 目录属主变 `shell`；app 进程 `listFiles()` **返回空/看不见**（FUSE 拒绝跨属主）；`chown` 无 root 报 `Operation not permitted` |
| `adb push` → `/sdcard/Download/` | app 能读单文件，但 **`listFiles()` 返回 null** —— targetSdk 37 + 无 `READ_MEDIA_AUDIO` 权限 |
| `run-as <pkg>` 读外部路径 | `Permission denied`（run-as shell 无 FUSE 挂载） |

**根因**：Android 11+ 分区存储 + FUSE。应用可访问的外部路径与「host/adb 写入的属主」
不再统一；API 34+ 又收紧了后台/跨属主访问。

**✅ 可行落点**：
```bash
adb push x.wav /sdcard/Download/x.wav
adb shell "cat /sdcard/Download/x.wav | run-as <pkg> sh -c 'cat > cache/x.wav'"
```
→ 文件属主变为 app，**无需任何权限**即可读。

**代码侧配合**：`SpikeViewModel.loadExternalInternal` 新增 `cacheSpikeInput()` 回退，
扫私有 `cacheDir`/`filesDir`；脚本 `sep_run.sh` 改用上述两步。

**教训**：**移动端自动化“把文件送进 app”的可行落点随系统版本变化**。
- 依赖属主的路径（外部 files）会被 FUSE 拒；
- 依赖权限的路径（Download/公共目录）会被 scoped storage 拒；
- **app 私有目录 + `run-as` 是最不依赖环境假设的落点**。
> 附带教训：验证 APK 是否含新代码要查**全部** dex（本项目是多 dex，
> `classes5.dex` 才装得下），只看 `classes.dex` 会误判“没编进去”。

## 阶段 M2 — 引擎探测 / 模型分组 / 导航壳 / EQ

### 坑 42. [★ EQ·重要] 平台 Equalizer 必须挂在「真实 ExoPlayer 的会话」上

**场景**：给播放器加 EQ（`android.media.audiofx.Equalizer`）。

**症状**：在 `PlayerViewModel` 里用 `player.audioSessionId` 挂 EQ → **总是 0**，
`Equalizer` 构造失败/无效果。

**根因**：N4 之后 VM 只持 `MediaController`（不是真实 ExoPlayer），
**AudioTrack 会话属于 Service 里的 ExoPlayer**。
`MediaController.getAudioSessionId()` 拿不到真实会话；且 controller 的
`onPlaybackStateChanged` 也不可靠触发。

**解法**：由 `PlaybackService`（持 ExoPlayer 的那侧）在 **STATE_READY** 时回调
真实 player（`onPlayerReadyForEq` 钩子）→ 拿到 `audioSessionId=10121` 再挂。
验证：`dumpsys media.audio_flinger` 看 session 上是否出现 `EqualizerBundle [Enabled]`。

**教训**：**把播放器下沉到 Service 后，任何“需要真实 player”的功能
（EQ、音频会话、部分回调）都要经 Service 暴露** —— 与坑 37（焦点）同类：
进程级/底层资源不再在 UI 层。

### 坑 43. [EQ] `audioSessionId` 在 READY 前也是 0（同坑 36）

**场景**：多轨 EQ，在 `load()` 后立即给每条 stem 挂 EQ。

**症状**：`multi-track EQ attached: 0 track(s)` —— 两轨的 `audioSessionId` 全是 0。

**根因**：轨刚 `prepare()` 时会话未建立，`audioSessionId == 0`；
**必须等各轨 `STATE_READY`**。与坑 36（异步 prepare 期间读 `duration` 恒为 0）**同源**。

**解法**：`attachMultiTrackEq` 给每条轨加 READY 监听，就绪后再挂。
验证：两轨各自不同会话（`10153`/`10161`）各挂一份，参数同步广播。

**教训**：**ExoPlayer 的“会话/时长/位置”类属性都要等 STATE_READY** ——
已第三次踩到（坑 36 时长、坑 42 会话、本坑会话），可视为一族。

### 坑 44. [环境] 测试设备会话之间会“重置”

多次观察到：设备在会话之间 app 的 `files/sherpa`、`files/uvr` 消失，
需重新 push 模型才能跑分离/benchmark。
**应对**：所有跑测脚本（`sep_run.sh`）应在开始前**幂等地重推**依赖
（测试音频、模型），不假设上一步的遗留状态。

## 阶段 M3 — 多轨+EQ 搬进 PlaybackService

### 坑 45. [★★ 关键] `ForwardingPlayer` 伪装 session player → 多轨无通知/无前台服务

**场景**：M3 想把多轨搬进 `PlaybackService`，但 `MediaSession.Builder` 只接受**一个** Player，
而多轨是 N 个 ExoPlayer。

**v1 错误做法**：写一个 `PlaybackRouter : ForwardingPlayer` 作 session 的唯一 Player，
内部在单/多轨间切、广播命令。

**症状**：**单轨正常；多轨时不出媒体通知、不进前台服务**
（`startForegroundCount=0`，无通知；但两轨确实在播、平台 `PlaybackState=PLAYING`）。

**试过且无效的 6 种补丁**：主轨加 `MediaMetadata` / router 的
`getCurrentMediaItem()/getMediaItemCount()` 取主轨 / **监听器中继**（转发多轨 player 事件）/
`triggerNotificationUpdate()`（立即+延迟）/ `setShowNotificationForIdlePlayer(ALWAYS)` /
`addListener` 同时调 `super`。

**已排除**：不是权限（`appops` 通知已允许）、不是播放（平台会话 `PLAYING`、两轨 `started`）。

**根因**：media3 的通知/前台服务机制对“**真实的、正在播放的、有 media item 的 Player**”
有硬依赖；**伪装 player 落入盲区**（特别是 media items 在自定义命令中才设置时）。

**✅ 正解（v2）**：**让 session 永远只认真实的 `singlePlayer`**；多轨的**主轨就是它**，
其余为“跟随轨”（不进 session）。
```
MediaSession(singlePlayer)   ← 永远
  单轨：播原始音频；多轨：singlePlayer 播主轨，followers 播其余
```
⇒ 多轨对 media3 而言与单轨无区别 → `startForegroundCount=1`、通知正常。

**教训**：**不要把框架的“单例语义”硬拗成“集合语义”**。media3 的 session 就是“一个 player”，
想要多轨应该**把它做成单个逻辑播放器（主轨+跟随）**，而不是**伪装成一个 player**。

### 坑 46. [多轨] 主轨复用外部 player 时不能 release 它

**场景**：v2 下 `MultiTrackController.load(..., externalPrimary = singlePlayer)` ——
主轨不再自建，而是复用 Service 的 `singlePlayer`（session 的 player）。

**隐患**：旧的 `releaseAll()` 无差别 `player.release()` → **会把 session 的 player 释放**，
导致退出多轨后整个播放链坏掉。

**解法**：`Track` 增加 `ownsPlayer: Boolean`（主轨=false）；`releaseAll` 只 release
`ownsPlayer=true` 的轨。

**教训**：**“谁的资源谁释放”** —— 借用别人的对象时，必须能区分“拥有”与“引用”。
（与坑 35“单一出口”、坑 37“进程级资源统一持有”同一族。）

## 阶段 M3.5 — M3 架构变更实测补强

### 坑 47. [多轨·回归] 退出多轨时用 `STATE_READY` 做 EQ 重挂门槛 → EQ 漏挂

**场景**：M3.5/T2 验证“单↔多轨切换”：多轨 → 退出 → 回单轨，期望 EQ 重新挂上。

**症状**：`exitMultiTrack` 执行了，但**没有 `attachSingleEq`** → 单轨 EQ 失效。

**根因**：`handleExit` 里写的是
`singlePlayer?.let { if (it.playbackState == STATE_READY) attachSingleEq(it) }`。
但退出多轨时，`singlePlayer`（刚当主轨）**已经不是 READY**（被停）→ 条件不成立。

**解法**：去掉 `STATE_READY` 门槛，无条件调 `attachSingleEq`
（它自身会判 `audioSessionId != 0`，session 为 0 时自然不挂）。

**验证**：修复后 `exitMultiTrack → attachSingleEq: audioSessionId=11137
→ Equalizer attached: session=11137`。

**教训**：与坑 42/43 同一族 —— **会话重建后必须重挂 EQ**。
额外一条：**重挂的门槛不能假设“player 处于 READY”**；
会话在非 READY 时也可能有效（如刚从多轨退出的主轨）。

### 坑 48. [JNI·★★ 误导性最强] JNI 里未初始化的 out 指针 → 误判为“运行时库有 bug”

**场景**：阶段 M4/S2，自写 JNI 调 ONNX Runtime 跑 htdemucs 模型（172MB）做可行性探针。

**症状**：ORT 正常加载（`version 1.28.2`）、模型正常创建（`session created in 1047ms`），
但一调 `api->Run(...)` 就 **native 崩溃**：先是 `SIGBUS BUS_ADRALN @0xa1eb090127`。
换了输入数据（随机 → 三角波 → **真实音频+真实 STFT**）**仍然崩**。

**错误结论（曾写入 .memory.md）**：“sherpa 自带的 ORT 1.28.2 在 arm64 上跑 htdemucs 图
有算子 bug / 与通用图不兼容”。

**真正根因（全在**我方** C 代码，两处）**：
1. `const OrtValue *outputs[2];` **声明未初始化**。一旦 `Run` 之前走到 `goto cleanup`，
   `api->ReleaseValue(outputs[i])` 就是**释放野指针**。
2. `CreateTensorWithDataAsOrtValue(...)` 的返回值既看状态码又不判**输出指针**是否为空；
   NULL 时后续 `Run` 解引用 → `SEGV @0x20`（NULL+0x20）。

**定位方法（关键）**：
- 加 `session input/output` 名称打印 → 确认名义无误（`input/x → output/add_67`）；
- **全程 NULL 判空 + 所有句柄置初值**；
- ★ **观察故障地址是否“漂移”**：同一 UB 在不同构建下落为
  `SIGBUS 0xa1eb090127` 与 `SIGSEGV 0x20` 两个**不同**地址 → 典型的**未定义行为**，
  **不是**某个固定函数里的稳定崩溃。

**修复后**：`PROBE_RESULT ORT_OK loadMs=1047 inferMs=9544` —— 一次跑通。

**教训（★通用）**：
1. **native 崩溃的第一嫌疑永远是“我方 JNI 的指针/句柄问题”**，而不是运行时库有 bug。
   运行时库（ORT/CUDA/…) 被广泛使用，真出 bug 的概率远低于我方的 C 代码。
2. **故障地址漂移 = UB；固定地址才更像库内部 bug。**
   前一轮正是因为两次都“崩在 Run 里”就草率归因，既误导了结论，又差点让项目
   整个放弃 Demucs 路线。
3. **结论要经得起“换个输入再试”的反复**：当“换数据仍崩”时，正确推论是
   “与数据无关”，而不是“库有问题”。

### 坑 49. [构建·★重要] Maven ONNX Runtime 与 sherpa AAR 的**符号版本精确匹配**冲突

**场景**：想给项目加 Demucs（需 ONNX Runtime），直觉方案是加 Maven 依赖
`com.microsoft.onnxruntime:onnxruntime-android`。

**症状**：`UnsatisfiedLinkError: dlopen failed: cannot locate symbol "OrtGetApiBase"
referenced by libonnxruntime4j_jni.so`。

**根因（符号级取证）**：
```
libsherpa-onnx-c-api.so  需要: (VERS_1.28.2) OrtGetApiBase   ← sherpa 自带 native
libonnxruntime4j_jni.so  需要: (VERS_1.22.0) OrtGetApiBase   ← Maven Java 绑定
libonnxruntime.so (APK)  导出:  VERS_1.28.2
```
ORT 的符号版本是 **精确匹配**（不是主版本兼容）；APK 里 `libonnxruntime.so` 只能
保留一份（`pickFirsts`）⇒ 只要 Maven 绑定版本 ≠ sherpa 自带版本，必然有一方解析失败。
而 Maven 只有 1.22.0/1.24.x/…/1.28.0/1.29.0/1.30.0，**没有 1.28.2**。
（另：`onnxruntime-android` 声明 **minSdk 24**，本项目是 23。）

**解法（已采用）**：**自写 JNI，直接链接 sherpa 那份 `libonnxruntime.so`**。
- 同一份 native ⇒ 符号版本天然一致（sherpa 的 c-api.so 就是这么链的）；
- 需：对应版本号的 `onnxruntime_c_api.h`（+ 其兄弟头文件）+ ~150 行 C 包装；
- 运行时 `System.loadLibrary("onnxruntime")` 后再加载我方库；
- 验证：`.so` 的 `GetApi(14..28)=Y, 29..=n` ⇒ 其 `ORT_API_VERSION=28`，与官方
  v1.28.2 头**完全一致**（这也是坑 48 能被排除的关键一步）。

**教训**：混合“自带 native 的 AAR”与“Maven 的同类库”时，**先查两者导出的符号版本**
（`objdump -T` / `nm -D`），不要假设“版本差不多就能共存”。
本项目 `cpp/ort-libs/` 即按 `sherpa-libs/` 同模式放置 ORT 头 + `.so`。

### 坑 50. [选型·★★ 隐蔽] Spleeter 4-stem 与 2-stem **架构/权形完全相同**，只有激活不同

**场景**：阶段 M4/S3，想给 sherpa 换上 Spleeter **4-stem** 模型（vocals/drums/bass/other）。

**症状（如果盲目套用）**：模型能加载、能跑、输出形状也对，但结果是**垃圾**
（实测 max error 945，而信号量程才 178 —— **误差比信号还大**）。

**根因**：Spleeter 的激活函数写在 **config JSON** 里，不在权重里：
```jsonc
// 2stems/base_config.json
"params": {}                                 // 默认 LeakyReLU(0.2) + ReLU
// 4stems/base_config.json
"params": { "conv_activation": "ELU", "deconv_activation": "ELU" }
```
⇒ **2-stem 与 4-stem 的权重形状 kernel-for-kernel 完全相同**，
一个 2-stem 形状的实现能**无怨无悔地**加载 4-stem 权重并输出垃圾。

**sherpa-onnx 为何只发布 2-stems**：其 `unet.py` 硬编码 LeakyReLU/ReLU，
且 Spleeter 配置结构只有 `vocals`/`accompaniment` 两个槽 —— 接不下 4 模型。

**解法**：4-stem 必须**自建 DSP**（走 ORT JNI）：
STFT（周期 Hann 4096/1024）→ 4 个模型（ELU，ONNX 图内已烘）= 幅度谱 →
**ratio mask**（分母需 4 个 stem 全部）→ 带扩展（用 `average` 而非 `zeros`）→ iSTFT。

**验证判据（★）**：不要听感，算 **`sum(4 stems) − mix`**；Spleeter 的 ratio mask
和恒为 1 ⇒ 应 ≈ **−153 dB**（实测我们的实现 −163.5 dB）。
若明显偏大，多半是 **窗函数**（周期 Hann vs 对称 Hann，差一个样本）或 **hop** 错。

**教训**：
1. **“形状兼容”≠“语义兼容”**；导出图里看不出激活时，必须回到**训练配置**确认。
2. 分离类模型的正确性优先用**重建不变量**（能量守恒）而非人耳；
   听感只能区分“好不好”，区分不了“对不对”（与坑 17 同族）。
3. 本项目已有两套“图只有一半、DSP 自己做”的案例（Demucs S2、Spleeter-4 S3）——
   后续新模型都应按“先核对契约（输入/输出/激活/STFT 约定）再动手”的流程走。

### 坑 51. [DSP·重要] Spleeter 4-stem 的两个“数值级”陷阱（都被单测拓到）

**背景**：自己实现 4-stem 的 STFT / mask / 带扩展 / iSTFT（`Spleeter4Dsp`）。
参照 Best-Practice README 的 Python 实现。两个 bug：

#### (a) 前补零量不是 center-pad 直觉值
参考实现的 `PAD = N_FFT - HOP = 3072`（**不是** `N_FFT/2 = 2048`）。
用错 → 帧数差 1（`ceil((PAD+len)/HOP)`：43 vs 42）、且 iSTFT 裁剪偏移错。
> 单测直接抓到：`frame_and_split_counts` 失败（expected 43, was 42）。

#### (b) iFFT 只用单边谱 → 重建幅度**恰好减半**
`stftChannel` 产出的是**完整 4096 bin** 复谱；若 iSTFT 时只填 `0..2048`
（未对称到负频率），iFFT 用了单边谱 → 重建幅度**恰好 0.5×**。
修：把 mask 对称地施到 `N_FFT-b ↔ b`。

**教训（★通用）**：
1. **误差是“整数比”（0.5 / 2 / 4）时，优先怀疑“少了一半/少了个因子”，
   而不是“精度不够”**。数字这么“干净”，说明是结构性错误，不是舍入。
2. **自建 DSP 必须做“重建不变量”单测**（`sum(4) − mix ≈ −∞ dB`）；
   它一次性覆盖 STFT + mask + 带扩展 + iSTFT 四个环节——正是它拓到了上面两个 bug。
3. **与参考实现交叉验证**（Kotlin STFT vs numpy <1%），证明是“数值等价”
   而非仅“自洽”。
4. 前补零 / 窗类型 / hop 这三个“STFT 约定”最易错（周期 Hann vs 对称 Hann
   只差一个样本，却是“匹配训练期”与“仅仅像”的分界）。

### 坑 53. [选型·★★ 误导性] Java API 有方法名 ≠ 该 EP 被编入二进制

**场景**：想验证“换 ORT 加 GPU/NPU 能快多少”。看到 `onnxruntime-android-qnn` 的
`classes.jar` 里 `OrtSession.SessionOptions` 有 `addXnnpack()` / `addQnn()` /
`addNnapi()` 三份方法 → 以为都能用。

**真相**：**Java 类是整个 ORT Java API 的共享实现**（带全部方法名），
但每个 AAR 的 `.so` **只编入了部分 EP**。调用未编入的 EP：
```
addNnapi()   → OrtException: "This binary was not compiled with NNAPI support"
addXnnpack() → OrtException: "XNNPACK execution provider is not supported in this build"
```

**正确姿势**：不要看 Java 方法，要看 **`.so` 导出符号 + `env.availableProviders`**：
- `nm -D --defined-only libonnxruntime.so | grep AppendExecutionProvider`
- 运行时 `OrtEnvironment.getAvailableProviders()`

**实测（Gen3，htdemucs 7.8s 窗，中位）：**
| EP | 结果 |
|---|---|
| CPU | 4237 ms（1.84×）|
| QNN（骁龙 NPU）| **3290 ms（2.37×）← 仅 1.29×** |
| NNAPI | ❌ 未编入 |
| XNNPACK | ❌ 未编入 |

⇒ 报告结论：**GPU/NPU 上限仅 ~1.3×**（非标准算子回退 CPU + 搬运开销），
**不值得为它重构**。实验产物：独立 `bench/` 模块（不引 sherpa，绕开坑 49）。

### 坑 54. [Compose·★重要] 可滚动列里 `aspectRatio(1f)` 会塌成 0 → Canvas 不画

**场景**：UI-V 黑胶转盘（`DeckView`）用自绘 Canvas，包在 `Column.verticalScroll{}` 里。

**症状**：代码无报错、Canvas 对应 View 存在，但**屏幕上一片纯黑（转盘完全不画）**。
截图像素统计：该区域 nonblack 比例 **0.0**。

**根因**：`Modifier.fillMaxWidth().aspectRatio(1f)` 需要**一个已知维度**来推另一个。
但垂直滚动容器给子项的**高度约束是 unbounded（Infinity）**——`aspectRatio` 无法
从“无穷高”推出宽度，最终**两条边都塌成 0** → Canvas 尺寸为 0 → 什么都不画。

**解法**：用 **`BoxWithConstraints`** 取可用宽度，直接定正方形边长：
```kotlin
BoxWithConstraints(Modifier.fillMaxWidth()) {
    val side = maxWidth            // Dp：滚动容器里宽度是有界的
    Canvas(Modifier.size(side)) { /* 绘制 */ }
}
```

**教训（★通用）**：
1. **自绘 Canvas 必须确保尺寸非零**；“没报错但什么都不显示”先查尺寸（截图算像素比例最快）。
2. **`aspectRatio` 依赖可推导的约束**；在 `verticalScroll` / `LazyColumn` 等
   无界高度容器里，它可能塌成 0。用 `BoxWithConstraints` + 显式 `size` 才稳。
3. 验证 UI 时，**截图 + 像素统计**（非黑比例、强调色像素数）是快速客观判据，
   比“看层次树里有没有节点”可靠（Canvas 无文本，层次树看不出画没画）。

### 坑 55. [Compose·隐蔽] Flow 没 collect → UI 状态永远不更新

**场景**：`WaveformExtractor` / `CoverExtractor` 产出 `StateFlow`，VM 里却没收集它。

**症状**：波形/封面**永远不显示**（state 字段一直是 null），但不报任何错。

**根因**：`PlayerState.waveform` 字段存在、`WaveformView` 也读它，但**从未有代码把

**解法**：在 VM `init` 里 `viewModelScope.launch { flow.collect { state = ... } }`。

**教训**：`StateFlow` 产出后**必须有人 collect** 才生效；换提取器/加新流时，
顺手确认“下游有接”。

**场景**：R3 转盘外环需“整曲波形”，提取时崩：

### 坑 58. [Compose·★] 高频状态源与低频状态源**不一致** → “点位对不上”

**场景**：转盘点外环 seek“点位对不上”（误差随进度累积）。

**根因**：`PlayerScreen` 里 **seek 用低频 `state.durationMs`**，而**绘制用高频
`progressFlow.durationMs`** → 两者不一致（state 滞后/可能为 0）→ `f * duration` 算错。

### 坑 59. [ExoPlayer·★★] `currentPosition` 在 seek 后**回退** + **非严格单调**

**场景**：① 拖进度条后“往回跳 1-2s”；② 读秒数字偶尔回退到上一秒。

**根因**：ExoPlayer 无进度推送（只能轮询 `currentPosition`）。而 `currentPosition`
从 AudioTrack 播放头推算，**seek 完成后会短暂返回旧值**，且平时**非严格单调**（小回退/抖动）。
直接显示其原始值 → 回跳。

**解法（两层，均低风险）**：
1. **seek 锁定**：`seekTo(T)` 时设 `pendingSeekMs=T`；轮询里锁定期用 T 兑底，
   `currentPosition` 追上（pos ≥ T-容差）后解除 → 消除 seek 回跳。
2. **单调化**：非 seek 期间 `pos = max(pos, lastShown)`（回退则保持旧值）→ 消除回退。
3. 可选：轮询间隔 **200ms→100ms**（采密，“读秒”更跟手）。

**教训**：**进度显示不能直接信任 `currentPosition`**，需“seek 锁定 + 单调化”两层保护。
另：“读秒不均匀”是“100/200ms 采样 vs 1s 显示粒度”的必然，非 bug；
插值平滑会显著提高重绘成本（转盘每帧重绘很重），性价比低。

### 坑 60. [★ 重踩·坑59] 单调化缺“大回退”分支 → 重播后进度卡死

**场景**：R3 加了“进度单调化”（非 seek 期间只允许前进）后，用户报“**播到末尾后再点播放，
有声音但转盘不转、进度不走**”。

**根因**：单调化假设“回退都是小抖动”，未处理**大回退**。播到末尾 `lastShownMs≈duration`；
重播时 `currentPosition→0` ⇒ `pos < lastShownMs` ⇒ 被单调化**压回末尾** ⇒ 永远不变。

**修法**：
1. 单调化只压制**小回退**（`back < MONOTONIC_TOLERANCE_MS=1s`）；大回退（重播/意外跳转）**接受**。
2. 监听 `Player.Listener.onPositionDiscontinuity`（seek/重播到头的权威信号）→ 重置 `lastShownMs`。

**教训**：**“只允许单调递增”类逻辑，必须同时定义“何时允许重置”**（否则一次异常回退就永久卡死）。

### 坑 61. [ExoPlayer·★★★] `currentPosition` 会“**停滞 ~800ms 再补跳**” → 进度 UI 卡/跳/回弹

**场景**：播放中，进度条数字 + 转盘动画（内环/中环）持续“卡/跳”，且 **1 倍速开头 ~3-4s
回弹一下**（加速则推迟）；**声音始终不卡**。

**★ 根因（实测确证）**：`Player.currentPosition` 有两个非理想特性：
1. **固定滞后 ~183ms**（音频播放头 vs 报值）；
2. **周期性“停滞”**：某位置读值**不变** ~300–800ms（实测 `pos=2950` 停滞 ~700ms），
   然后**一次“补跳”**到位（AudioTrack 播放头更新粒度）。

**为何会卡/跳/回弹（两个叠加故障）**：
- **外推 vs 真实**的 drift 在停滞期从 ~183ms 涨到 ~800ms；若重锚阈值 < 停滞幅度 →
  停滞被误判为“漂移” → **重锚把锚点硬拉回** → **一次性跳**。
- 重锚往往**连续几帧触发**；平滑层若**累加**捕获量 → **过度补偿 → 回弹**。

**修法（三层，缺一不可）**：
1. **锚点外推（本地时钟）**：`pos(now)=positionMs+(now-realtimeMs)×speed`（见 `UiClock`）。
2. **大阈值 + 保守重锚**：`ANCHOR_DRIFT_TOLERANCE_MS = 1800ms`（> 停滞幅度）；
   且需**连续两次**超阈；离群采样不参与。→ 停滞期**不重锚**。
3. **平滑捕获（缓追）**：`rememberSmoothPosition` 每帧 `disp=外推值+delta`；锚点实质变化时才把差值
   计入 `delta`，再逐帧衰减；**捕获冷却 300ms 内“替换而非累加”**。
   ⚠ 平滑层判“锚点是否变化”的 key **不能含 `realtimeMs`**（每轮询都刷新 → 误判 → 反复吞 delta → 回弹）。

**教训**：
- **`currentPosition` 不可直接驱动 UI**（既滞后又会停滞）。进度 UI 需：
  **本地时钟外推 + 缓追 + 容忍停滞**。
- “外推领先于报值”在**停滞期反而是对的**（声音仍在播）⇒ 阈值要**大于**停滞幅度。
- 调试此类问题：分别打印**原始 `pos` 序列**与**drift**（我加的 `POSDELTA`/`[T]` 日志），
  不要只看“位置变了没”。

### 坑 62. [★ 缓存] 流式提取“中途取消”的**半截结果**被写入缓存 → 命中后残缺

**场景**：波形缓存引入后，**某一首歌**（如“喀秋莎”）波形“**卡在一半**”（只显示前几十秒）。

**根因**：`extractFromExtractor` 是**流式**（逐块 emit）；当它**被取消**（切歌）或**中途终止**时，
返回的是“**已解码的部分**”。而早期代码**无条件 `WaveformCache.save(...)`** → **把半截波形当完整缓存**。
之后命中该缓存 → 永远显示残缺（直到清缓存）。

**证据**：`waveform(cache hit): points=1047, dur=20938ms`（只 20s，非全曲）+ 缓存文件 ~8/43/54KB（完整应 ~125KB）。

**修法**：提取返回 **`ExtractResult(data, complete)`**（`complete = decodeToPcmStreaming` 是否**正常跑完**）；
**只在 `complete` 时写缓存**。已污染的缓存需**手动清**（`rm -rf files/waveform-cache`）。

**教训**：**缓存“流式/可中断”的结果前，必须先确认“完整”**，否则会把中间态当终态缓存。

### 坑 63. [SAF·★] 文件夹导入未持久化 tree 权限 → 播放报 `ERROR_CODE_IO_UNSPECIFIED`

**场景**：导入文件夹歌单（如 `Music/`）后，点里面的曲目播放 → `ERROR_CODE_IO_UNSPECIFIED`。

**根因**：`OpenDocumentTree` 返回的是 **tree uri**；须对其调 `takePersistableUriPermission`，
否则 **app 重启/后续访问子文档** 时报：
```
SecurityException: Permission Denial: reading content://.../tree/primary%3AMusic/document/...
  requires that you obtain access using ACTION_OPEN_DOCUMENT or related APIs
```
（当初 `PlayerScreen` **导入单文件**时做了持久化，但 **选文件夹**漏了。）

**修法**：`PlaylistScreen.pickFolder` 回调里加
`contentResolver.takePersistableUriPermission(uri, READ|WRITE)`。
⚠️ **已导入的旧文件夹歌单不会自动补权** → 需**重新选文件夹导入**。

**教训**：**凡是 SAF 返回的 uri（单文件 + 文件夹）都必须 `takePersistableUriPermission`**，
否则只在“本次会话内”可读。

### 坑 64. [Compose·★★ 与坑58同族] 逐帧状态在 **composition 阶段**读 → 无限重组 → Compose 永不 idle

**场景（发现）**：`connectedDebugAndroidTest` 真机 BF00A → **`PlayerUiTest` 6 项全挂**，
栈均为 `ComposeNotIdleException: Idling resource timed out ... pending recompositions`，
并提示 `most likely infinite re-compositions happening in the tested code`。
⇒ 测试**还没走到断言**就超时（不是断言问题）。

**根因**：`ProgressBar.kt` 有一个“每帧失效”机制：
```kotlin
var frameTick by remember { mutableIntStateOf(0) }
LaunchedEffect(Unit) { while (true) { withFrameNanos { frameTick++ } } }  // 无 isPlaying 守卫
frameTick  // ← 在【composition 阶段】读一下
```
- 写 `MutableState` + 在 **composition 阶段**读 → 每帧触发**重组**（不是“只重绘”）；
- `LaunchedEffect(Unit)` 的 `while(true)` **无 `isPlaying` 守卫** → **静止不播放时也每帧重组** → 永不 idle。

**为何 `DeckView` 没踩**：同样模式，但① `frameTick` 读在 **Canvas draw lambda 内**（draw 阶段读 → 只失效重绘），
② 带 `if (isPlaying)` 守卫。`ProgressBar` **两者皆缺**。

**修法**（照搬 `DeckView` 已验证写法）：
1. 逐帧值（`frameTick` / `smoothPos`）从 **composition 阶段** 移到 **draw 阶段**（Canvas lambda 内）读；
2. `frameTick++` 加 `isPlaying` 守卫（从 `anchorFlow.value.isPlaying` 取，`Progress` 无此字段）；
3. 时间 `Text` 改从 10Hz 的 `progressState` 取值（平滑交给 draw 阶段）。

**验证**：仪器化 **1过/6挂 → 3过/4挂**（`ComposeNotIdleException` **全消失**）→ 修 `PlayerUiTest` 旧断言后 **7/7 全绿**；单测 128/0。

**教训**：“每帧失效”只能读在 **draw 阶段**；在 composition 阶段读每帧变化的 `State`
= **无限重组**（耗电/掉帧，且 `waitForIdle` 类测试永不通过）。与坑 58（高频/低频状态源不一致）同族。

### 坑 65. [CI·★★ 连环坑] GitHub Actions 跑 Android CI 的 4 层连环失败

**背景**：仓库迁到 GitHub 后开 CI（轻量版：只跑 `:app:testDebugUnitTest`），连续失败 4 次。
逐层剥开如下（后一层只有在前一层修好后才会暴露）：

| 层 | 现象 | 真因 | 修法 |
|---|---|---|---|
| 1 | 25s 失败 | `compileSdk 37` 是**预览版**，runner 上装不上 | —（先尝试降级） |
| 2 | 降 36 仍失败 | `android-actions/setup-android@v3` 的 `packages` 输入**静默没装上** platform | 改为**直接调 runner 预装 SDK 的 `sdkmanager`** + 断言目录存在 |
| 3 | 仍失败 | **阿里云 maven 镜像 502**（不代理 `org.jetbrains.kotlin:*`），而 settings 里它是唯一 google 源 | **官方仓库优先**（`google()`/`mavenCentral()` 在前），阿里云仅作补充 |
| 4 | 又失败 | 降 compileSdk 36 → `checkDebugAarMetadata` 失败（多个 AndroidX 依赖**要求 compileSdk>=37**）| **放弃降级**，用 `sdkmanager --channel=3` 装 API 37（预览渠道）|

**★ 关键技巧（日志拿不到时）**：仓库日志下载 API 需要 admin 权限。
解法：在 workflow 失败分支里把 Gradle 报错打成 **`::error::` annotation**，
再用公开的 `GET /repos/{owner}/{repo}/check-runs/{id}/annotations` 读到具体错误。

```bash
# 拿 annotation（公开仓库，无需 token）
CR=$(curl -s "$API/repos/$OWNER/$REPO/actions/runs/$RID/jobs" | grep -o '"check_run_url": *"[^"]*"' | head -1 | grep -oE '[0-9]+$')
curl -s "$API/repos/$OWNER/$REPO/check-runs/$CR/annotations"
```

**教训**：
1. **降 compileSdk 不是选项**——现代 AndroidX 硬要求高版本；"装不上 SDK"要往**装对渠道**（`--channel=3`）走，不是往下降。
2. **第三方镜像不能当唯一源**（会 502、会漏包）——官方源在前，镜像在后。
3. **action 的 `packages` 输入可能静默失败**——自己 `sdkmanager --install` + `test -d` 断言更可靠。
4. 私有仓库踩 CI 时，**先把仓库设 Public** + 用 annotation 技巧，能省大量来回。

### 坑 66. [仓库卫生·★★ 公开前必做] 大二进制入库存 → 仓库 300MB

**现象**：`git push` 前后仓库 `.git` 达 **300MB**；`bench/build/` 下 195 个构建产物（含 79.8MB 的 `libQnnHtpPrepare.so`、75MB `.apk`）被跟踪；
`model_assets/`（52MB 模型）、`doc/*.mp3`（音频）也在库中。

**根因**：`.gitignore` 只写了 `/build`（根目录），**没写 `**/build`** —— 子模块 `bench/build` 全被跟踪。

**修法**（公开前必做）：
1. `.gitignore` 补 `build/`、`**/build/`、`/model_assets/`、`*.onnx`、`*.tar.bz2`、`doc/*.mp3` 等；
   ⚠️ 但**保留构建必需的** `app/libs/sherpa-onnx-*.aar` 与 `app/src/main/cpp/ort-libs/*.so`（别用 `*.aar` 通配）。
2. `git rm --cached` 停止跟踪（文件仍在磁盘）。
3. **重写历史清除旧 blob**：`git-filter-repo --invert-paths --path ...`（`.git` 300MB → 69MB）。
4. 重新 `git remote add origin`（filter-repo 会移除 remote，属正常保护）。

**教训**：
- **`.gitignore` 的 `/build` 不覆盖子模块**，必须 `**/build/`。
- **源码仓库不要包含**：构建产物、模型权重、音频素材。
- 公开前先 `git ls-files | xargs ls -la | awk '$5>1e6'` 查一遍大文件。
- 私人/半公开服务地址（代理/内网域名）**不要写进源码**（哪怕只是注释）——别人 clone 后无法构建，且有信息泄露风险。

**附：模型许可（公开分发前必查）**
| 模型 | 许可 | 商用 |
|---|---|---|
| Spleeter（代码+权重）| MIT | 一般可 |
| Demucs | MIT | 一般可 |
| **UVR / MDX-Net 系列** | **各模型不同** | **部分仅限非商业/研究** |

⇒ App 内“一键下载模型”时，**每个模型弹窗须写明其各自许可**，不可统一写 MIT。

### 坑 67. [环境·★ 误导] 重装 APK 会清空应用私有目录 → 模型/音频/缓存全没

**现象**：重装 APK 后，播放器没有波形、分离报“模型缺失”、导入的歌曲也消失了。

**根因**：本项目依赖的数据全在**私有目录**——模型 `files/sherpa/`、测试音频
`files/`、分离缓存 `files/stems-cache/`、波形缓存 `files/waveform-cache/`。
重新安装（尤其先 uninstall 或数据被清）后全部丢失，必须重新推。

**正确推送方式**（避开坑 41 的权限问题）：
```bash
adb shell "run-as $PKG mkdir -p files/sherpa"
adb push model_assets/.../vocals.fp16.onnx /data/local/tmp/v.onnx
adb shell "run-as $PKG cp /data/local/tmp/v.onnx files/sherpa/vocals.fp16.onnx"
```

❗ **不要**用 `run-as $PKG sh -c 'cat /sdcard/... > files/x'` —— 实测曾产出
**0 字节文件**，之后播放才报 `UnrecognizedInputFormatException`，很容易
误判成代码 bug。

**教训**：排查“文件读不出来”之前，**先用 `run-as ls -la` 看文件大小**。

### 坑 68. [方法论·★] “看不见”不等于“没画”：先量化再下结论

**现象**：报告换浅色主题截图后，直觉上认为“转盘外环波形没画出来”。

**像素统计（实测）**：

| 主题 | 波形像素 | 角向覆盖 |
|---|---|---|
| 深色 | 25,400 | 27/36 段 |
| 浅色 | 24,738 | 27/36 段 |

**结论**：波形一直都在。`WaveRemaining = 0xFF37474F`（深灰蓝）在浅色背景上
**细线对比度低**，于是“看着像没有”。

**教训**：UI 视觉问题不要凭肉眼定性。先用像素统计（数量 + 几何分布）建立事实，
再判断是“真的缺失”还是“对比度/尺寸问题”。与坑 38/39 同族：
**先保证可观测性，再谈结论**；否则会为了“修复”一个不存在的 bug 白费工夫。

### 坑 69. [数据/算法·★] 参与完整性判定的常量必须是**实测真实值**，不能是抹零估值

**现象**（2026-10-20 真机实报）：模型库点「下载」UVR 9482 → 进度到 100% → 返回再进来 →
**仍显示「下载（30 MB）」，`已装 3/8` 不变**。文件明明在磁盘上。

**排查**：
```bash
adb shell run-as pub.miku.neuralstem ls -l files/uvr/UVR_MDXNET_9482.onnx
# -rw------- ... 29704738  UVR_MDXNET_9482.onnx     ← 真实 29,704,738 B
```
而 `ModelCatalog` 里写的是 `28_300_000L` —— 差 **1,404,738 B**。

**根因**：`ModelCatalog.isInstalled()` 用 `SIZE_TOLERANCE_BYTES`（**±64KB**）比对
`expectedBytes`。估值与真实值差 1.4MB（大模型档差 3MB）→ 判定永远失败 →
UI 永远“未安装”，且**下载完还会被当成未安装重新下载**（白耗流量）。

**修**：`UVR_SMALL_BYTES = 29_704_738L`（9482/KARA）、
`UVR_LARGE_BYTES = 66_759_522L`（Voc_FT/Inst_HQ_3/Main，三者实际最大偏差 3.3KB ≪ 容差）。

**教训**：
1. **凡是参与判定的常量都用真实值**；“28MB”这种人间可读估值只能放在文案里。
2. 与坑 67 同族：**下载完 = UI 变了** 是最容易漏的验收点。验收时必须
   `返回→再进入` 看**持久状态**（磁盘 + 已装计数），而不是只看下载当下那一屏。
3. 已加回归测试 `ModelCatalogTest.UVR 期望字节数必须是真实值而不是抹零估值`，
   写回抹零估值会立刻失败。

**另（同时修的显示问题）**：模型库的折叠节状态原先只在首次组合时按“含已装模型的节”
初始化、此后不再跟随 → 下载完成后新装的节仍可能显示为折叠，用户看不到那一行。
改为 **自动展开（含已装模型）∪ 用户手动展开 − 用户手动折叠** 三集合派生。

### 坑 70. [方法论·★★] 布局/视觉问题单测抓不到 —— 逻辑靠单测，布局靠真机截图

**背景**（2026-10-20 一天内连踩三个）：

| # | 现象 | 单测能抓吗 | 根因类型 |
|---|---|---|---|
| 1 | 模型下载完，返回再进仍显示未安装 | ❌ | 常量值错（1.4MB 偏差超容差） |
| 2 | 横屏模型列表被推出屏幕外 | ❌ | `Scaffold` 套嵌 → insets 算两遍 |
| 3 | 右侧栏第一项压状态栏、最后一项贴屏底 | ❌ | dp/px 混淆 + 未均分 |

三个 bug 全部**通过**了当时的 198 条 JVM 单测。

**为什么单测抓不到**

- 单测断言的是**函数返回值**（`isInstalled() == true`），不是**用户看到什么**。
  常量错了 → 单测也在用同一个错常量，自洽通过。
- 布局问题是 `Modifier` 链的**运行时几何**，Compose 单测（`createComposeRule`）
  要跑仪器化，项目当前没有这套基建。
- 而且这三个都不是"写错了逻辑"，是"**写对了逻辑但用户看到的东西不对**"。

**这次怎么发现的**

全部靠 **`uiautomator dump` 读真实 `bounds`**：

```bash
adb shell uiautomator dump /sdcard/u.xml && adb pull /sdcard/u.xml
# 然后断言几何：内容区高度、元素是否超出屏幕、间距是否均匀
```

例如坑 2 的判定依据：
```
内容区 scrollable: [192,320][1600,560]   ← 左侧空 192px、高只有 240px
```

坑 3 的判定依据：
```
导航项中心 y = 56 / 176 / 296 / 416 / 576
状态栏 frame = [0,0][1600,96]            ← 第一项 56 < 96 = 被压住
屏幕高 720，最后一项结束于 592            ← 底部空 128px
```

**教训**

1. **验证手段要匹配问题性质**。逻辑 bug → 单测；视觉/布局 → 真机 + 几何断言；
   音频 → `dumpsys media.audio_flinger`（不是耳朵）。
2. **"编译通过 + 单测全绿"不等于功能正确**。凡是涉及 UI 的改动，
   必须在真机上读一次实际 `bounds`，而不是"看截图觉得没问题"。
3. **数值问题先算清单位**。坑 3 里我把 96px 当 96dp 算，
   导致"顶部 1/3" 算成 32dp（实际应是 16dp），第一次改完仍然偏。
   Compose 里 **dp ≠ px**，`320dpi` 下 1dp = 2px。

**与既有坑的关系**

- 坑 68（先量化再下结论）：同样主张"不要靠肉眼"。
  本条是它的延伸 —— **量化** 除了像素统计，还包括**几何 bounds**。
- 坑 20/32（禁止坐标点击、应用内自驱动）：
  注意 `uiautomator dump` 只用来**读**(dump)，不用来**点**(input tap)。
  读数据不受那条纪律限制，因为它不改变应用状态。
