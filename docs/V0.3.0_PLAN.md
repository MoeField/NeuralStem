# v0.3.0 结构重构方案（实施中）

> 状态：**第一刀（AudioSink 抽象 + I2/I3 测试）已完成，v0.3.0 已发布**。
> 基线：v0.2.66（JVM 512/0，2h soak 零错误，发布链路全绿）。
> 原则：**只改结构，不改行为**；每一步都保持可发布、可回退。
> 本文只记录 v0.3.0 第一刀（AudioSink 抽象）；服务/VM 拆分留到 v0.3.1+。

## 1. 为什么先做 AudioSink（P1-14）

REVIEW 多次指出：`StemMixer` 的 I1–I3 不变量（渲染线程存活、write 失败重建、曲尾收尾）
是**最贵的重构，却没有安全网**——因为音频输出直接绑死 `android.media.AudioTrack`，
JVM 测试无法构造。

先抽象输出层，才能：

- 用 `FakeAudioSink` 在 JVM 里复现「write 返回负值 → 重建 → play → 继续推帧」
- 复现「曲尾 Sonic 排空后 writer 正确收尾」
- 后续拆 `PlaybackService`/`PlayerViewModel` 时，有回归网兜住音频路径

## 2. 范围

### 做

1. 新增 `AudioSink` 接口：
   - `audioSessionId`、`frameCapacity`
   - `play/pause/flush/release`
   - `write(FloatArray, len)`、`write(ByteBuffer, len)`（Sonic 输出是 ByteBuffer）
2. 新增 `AudioTrackSink`：现有 `AudioTrack` 逻辑原样搬入（Builder、buffer 大小、session 回调）
3. `StemMixer` 构造注入 `sinkFactory`（默认 `AudioTrackSink`），内部 `track` 全替换为 `sink`
4. 新增 `FakeAudioSink`（`app/src/test`）：可注入 write 失败、记录写入/重建次数
5. 补测试：
   - **I2**：write 失败 → release + 重建 → play → 继续推进（不静默停）
   - **I3**：曲尾 `stage.finish` 排空后 `ended=true`、`running=false`，可再次 play 重启

### 不做（v0.3.1+）

- 拆 `PlaybackService`（882 行）/ `PlayerViewModel`（2529 行）
- 改 MediaSession 门面模型
- 改 `SeparationService`/`SeparationRepository` 分层

## 3. 验收

| 项 | 标准 |
|---|---|
| 行为等价 | 真机：单曲/多轨播放、seek、变速变调、EQ、退出多轨无回归 |
| 新增测试 | I2/I3 各≥1 条，失败注入可复现 |
| 基线 | JVM ≥512/0、lint 通过 |
| 发布 | v0.3.0 走同一 CI/F-Droid 链路 |

## 4. 风险与回退

- `StemMixer` 是音频核心：任何改动都可能引入无声/卡顿。
  - 缓解：`AudioTrackSink` 只是搬运原逻辑，不改参数；改完立即真机 smoke。
  - 回退：单 commit 可 revert，sinkFactory 默认值保证旧路径。
- `FakeAudioSink` 不能完全模拟 AudioTrack 的阻塞写语义：
  - 测试聚焦「失败/重建/收尾」状态迁移，不测真实时序。
