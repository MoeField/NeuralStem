# 代码/架构评审约定（从 REVIEW 漏检反推）

> 来源：2026-11-23 `CodeReviewKit/04_架构评审单页.md` + `.review/REVIEW.md`。  
> 目的：把“这次为什么没提前发现 P1-1/P1-2/P1-3”变成下一轮的检查动作，而不是只写复盘。

## 0. 为什么之前没发现

| 漏检点 | 当时怎么测的 | 为什么测不出 |
|---|---|---|
| 主线程多轨 load/join | 2h 随机 soak、功能 smoke | 只断言“最终能播/不崩”，没有测**主线程耗时**与**调用线程** |
| 共享 `voices`/增益无同步 | 多轨播放/静音全过 | 功能测试在单线程/低竞争下也“看起来对”；没有并发写 + 读断言 |
| 导出先删后写 | 正常导出成功 | 只测成功路径；没有“写新失败时旧文件是否还在”的故障注入 |
| I1–I5 无守护 | 有 KDoc/手工 `mixfail` | 手工 hook 只触发、无断言；测试数量被当成不变量覆盖 |
| 死代码被当机制 | 看 KDoc/接口名 | 没有 grep 调用点，没有“文档承诺 = 实现调用”的检查 |

共同根因：**测了行为结果，没测结构约束；测了成功路径，没测失败路径；把注释/接口当成已实现。**

## 1. 评审前必须取的五张表

对齐 `04_架构评审单页.md`：

1. 模块图（`settings.gradle.kts` include + `build.gradle.kts`）
2. 依赖方向（`project(":x")`，反向 import）
3. 入口/生命周期（Manifest、Application、Service）
4. 状态真源（`MutableStateFlow|LiveData|MutableState` 的**写者**）
5. 线程模型（`Dispatchers.|Thread(|Handler(|Executors.` 的**所有者**）

没有表不进入结论。

## 2. 六个“必须问”的问题

对每个改动/评审点：

1. 这段代码**在哪个线程**执行？调用者是谁？
2. 主线程上有没有 `File`、`join`、`sleep`、`runBlocking`、大 JSON？
3. 有没有**两个写者**共享可变容器/普通 `var`？读侧有没有 happens-before？
4. 失败/取消/超时后，资源与用户数据是否保留？有没有“先删后写”？
5. 文档/接口承诺的机制，**有没有实际调用点**？（grep 验证）
6. 这条不变量有没有**自动化守护**？故障注入时断言了什么？

## 3. 四类必须补的测试

| 类型 | 例子 | 判定 |
|---|---|---|
| 线程/主线程 | StrictMode `detectDiskReads`；命令返回 <16ms；Perfetto | 主线程零文件 IO/join |
| 并发 | 快速拖音量/切轨；读写快照 | 无旧增益、无半更新容器 |
| 破坏性操作 | 导出中途失败、磁盘满、权限拒绝 | 旧文件/旧数据仍在 |
| 不变量 | I1/I2/I3/I4/I5/J1/J3 | 有断言，不是只触发 hook |

新增功能至少补一条**失败路径**测试；只加成功路径不算完成。

## 4. PR / 发版门禁

### 每个 PR

- [ ] 主线程无新增 `File`/`join`/阻塞调用
- [ ] 新增共享可变状态 → 不可变快照/锁/单写者，并写 KDoc
- [ ] 新增“删除/覆盖”操作 → 先写后删，失败保留旧数据
- [ ] 新增文档承诺 → grep 调用点/测试
- [ ] 新增失败分支 → 有测试或明确“不可测原因”

### 发版前

- [ ] 架构评审 5 张表 + 3 个结构性问题结论
- [ ] REVIEW 中 P0=0、阻断 P1=0，且有 owner/验证证据
- [ ] release 包 clean install + 升级 smoke
- [ ] 关键不变量测试（I1–I5）至少覆盖破坏路径
- [ ] 文档索引/断链检查通过

## 5. 评审结论写法

不要只列 finding。用 ADR 风格：

1. 一句话判断（撑不撑得住接下来 3 个月）
2. 三个结构性问题（证据 file:line + 影响的未来改动 + 最小结构改动）
3. 维持现状的决定（防止下轮重复讨论）
4. 下一步按投入产出排序
